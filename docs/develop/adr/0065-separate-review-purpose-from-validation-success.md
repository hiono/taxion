# レビュー目的と検証の成功条件を分離する

## Context

持込み成果物を Coder の成功から分離しても、全レビューの入口で検証コマンドの合格を要求すると、
失敗原因を調べる診断や、追加編集のない試行記録のレビューを開始できない。
文書だけのレビューに無関係なコマンドを追加する対処も、実行権限と証拠の意味を曖昧にする。

既存の `review-input.v1` は、必須コマンドの合格後に診断または品質レビューへ進む契約である。
保存済み契約の解釈を変えず、目的に応じた検証方針を明示して承認する必要がある。

## Decision

`review-input.v2` に `validationMode` を追加する。
`required-pass` は必須コマンドの合格を要求する。
`observe` は診断だけに許可し、正常終了したコマンドの失敗を `OBSERVED` として保存する。
保存記録だけを調べる診断では、実行コマンドを空にできる。
`identity-only` は実行コマンドを空にし、その理由を `validationSummary` に記録する。
どの方針でも対象の固定、設定と権限、期限、実行の所有権、結果受理の検査は省略しない。

方針は既存の immutable な Task decision と承認・工程計画へ結び付ける。
診断入力の完了は `NOT_ASSESSED_DIAGNOSTIC` であり、製品の品質・公開 gate を通さない。
出典や失敗状況を目的へ変換する専用ロール、偽の Coder 成功結果、汎用工程エンジンは追加しない。

入口、正式結果の検証、コンテキスト表示、保存監査、停止・復旧で同じ方針を使う。
`PASSED` と `OBSERVED` の適格性を共通判定し、後者を成功へ書き換えず正式に引き継ぐ。
対象は未コミット tree、コミット済みの対象、差分のない既存対象を区別して保持する。
コミット済みの対象は承認した baseline の子孫であることを確認し、両 SHA と全差分を保存する。

## Alternatives considered

全目的でコマンド合格を要求する案は、失敗診断を開始できないため採用しない。
v1 を緩める案は、保存済み承認の解釈を変えるため採用しない。
別の診断実行基盤を作る案は、対象照合・結果受理・復旧を二重化するため採用しない。

## Consequences

失敗したコード・文書・テスト、編集を残せない試行記録を診断できる。
コマンドが設定されている場合は入力段階と Reviewer 結果受理段階の両方で実行するため、
過去の配送不明な操作を再送する目的で設定してはならない。
中断や対象改変を「観測できた失敗」として受理することもない。

## Compatibility

旧形式は従来の厳密な検証を維持する。旧 binary は v2 を未知形式として拒否する。
v2 の保存前に workspace と Git の保持対象を保全し、旧版への rollback はその保全状態から行う。
新形式を保存した store に旧版を書き込ませない。

## Security and operational impact

Git 外の証拠は承認した入力内の引用か、固定した対象内の読取り可能な資料として渡す。
管理 DB や元セッション全体へのアクセスを Reviewer に与えず、秘密や職場固有情報を公開記録へ含めない。
artifact Flow 内の自動修正、任意 packet 委譲、restore 後の直接実行は引き続き未対応であり、
修正が必要なら既存の正式な実装後続契約を使う。
