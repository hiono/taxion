# 0055: 承認済みの目的に沿って全機能で柔軟に対応する

## 状態

採用。Issue #196。Taxion 全体に適用する設計判断であり、今回の承認束の変更だけに限定しない。既存機能の改善、新機能、運用手順、管理スキルの判断基準とする。個別の自動化は段階的に実装し、配布と製品状態への適用は別工程とする。

## AI 導入の目的と適用範囲

Taxion に AI を導入する目的は、状況の変化や不完全な情報に対応し、利用者の目的へ作業を進めることである。決められた手順をそのまま反復し、想定との差を利用者へ返すだけの運用を標準にしない。Taxion は製品開発のためのツールであり、Taxion 自身の形式整備や一般化のために対象製品の開発を止めない。

この判断は依頼の整理、計画、実装、検証、独立レビュー、役割間の連携、モデルやツールの選択・更新、設定、停止・復旧、公開、CLI と文書の全体に適用する。既存の特定コマンドだけに例外を追加して終わらせず、同じ判断を要求する入口には共通の処理と方針を適用する。

共通の実行方針にもこの判断を反映し、ready・Planner・質問・Coder・Reviewer とカスタム担当の指示に一度ずつ含める。指示だけで controller の機能が増えたとは扱わない。新しい指示は新規 session の構成要素であり、旧 session の設定 hash や保存した指示をこの変更に合わせて書き換えない。

## 目的と制約を守り、手段は状況に応じて選ぶ

利用者が承認する対象は、目的・受入れ条件・作業範囲・権限・残予算・期限・公開条件である。AI と controller は、その範囲で調査方法、実装手段、工程の組合せ、許可された再試行や代替手段を選ぶ。利用者が具体的な方法を必須条件にしている場合は、その条件も保つ。成果の保全、出典、二重実行防止、秘密情報の保護は手段を変えても維持する。

モデルの出力は直前の会話によっても変わる。同じ版・入力・ハッシュから同じ応答が得られることを、利用可能性や品質の前提にしない。成果は実際の受入れ条件、実行した検証、同一成果物の独立レビューで評価する。実行条件やハッシュの記録は取り違えや改変の検出に使い、それだけで正しさを保証したと扱わない。

既存情報で判断できることは、保存記録や現在の観測を先に調べる。承認範囲内で修正可能な方法を選べる場合は、その方法で作業を進める。外部接続の一時失敗なら許可された範囲の再確認や代替経路を使い、旧セッションへ接続できなければ保存成果からの正式な継続を検討する。同じ失敗の無制限な再試行、配送不明の命令の再送、受入れ条件の切下げは代替手段としない。

## 人間への確認は判断が変わる差分に限る

内部処理の順序、記録形式、互換性のある版変更だけを理由に、同じ意思決定を取り直さない。確認が必要な場合は、何が変わり、目的・品質・権限・費用・期限にどう影響し、どの判断が未承認なのかを具体的に示す。関連する判断はまとめ、同じ情報を別のフォームで繰り返し入力させない。既存の正式な意思決定から複数の内部記録を導出できるようにする。

範囲や権限の拡張、新しい予算・期限・公開許可、解消できない安全上の不確実性には新しい判断が必要である。人間の回答で解決しない技術的な失敗は、無関係な承認を求めず原因と可能な対処を示す。既存の判断がない、撤回された、または確認がキャンセルされた場合に、AI が承認済みと創作することは認めない。

この方針は [ADR-0036](0036-prioritize-approved-goals-over-token-thresholds.md) と [ADR-0040](0040-constrain-goal-oriented-efficiency-by-quality-evidence.md) の目標達成と品質証拠の方針を全機能へ具体化する。既存 ADR の hash 検証や明示承認は、記録保護と実際の権限のための条件として保つ。重複確認を生む箇所は、正式な承認の再利用と機械的な照合へ変更する。未改修の実行入口をこの文書だけで迂回したり、将来の自動化を利用可能と扱ったりしない。

## 変更時の判断と回帰試験

### 全工程で使う判定順序（仕様追補・個別実装は未完了）

計画、Coder 提出、結果ファイル受理、Controller 検証、Reviewer 引継ぎ、停止・復旧、
公開の全入口で、次の順序を共通にする。

1. 保存済み承認から目的・範囲・権限・予算・期限を確認する。未承認の拡張を推測しない。
2. agent の申告と、Git・実行記録・承認記録から Controller が確認できる事実を分離する。
   機械的に確定できる一覧・識別子・内部参照は Controller が導出し、申告の形式差だけで
   追加モデル・再提出・repair 消費・再承認を要求しない。未確認の事実は創作しない。
3. 実成果物と品質証拠を評価し、承認済みの次工程へ接続する。工程ごとに同じ情報を
   再申告させない。検証不合格、未実施の独立レビュー、実際の権限不足は形式差と区別する。
4. 新しい判断が必要なら、変更差分・影響・既存承認で足りる部分をまとめて提示する。
   承認後はその出典から必要な内部記録を導出する。監視や HOLD の記録だけで解決とはしない。

例えば Coder の変更一覧は、持込み分を含めた baseline から candidate までの全差分を
Controller が Git から確定する。申告原文と確定証拠は別に保持し、検証・独立レビュー・
公開前照合まで同じ candidate と確定一覧を使う。Reviewer 自身の変更一覧は空のままであり、
Coder の全差分を Reviewer の編集として補完しない。具体的な受理条件は
[Task Graph の変更一覧仕様](../task-graph.md#関係と実行契約)を正とする。

scope や fileAccess の不足は、必要な読取りと編集を分けて差分承認へ接続する。
承認済みの追加を後続契約へ反映する際も、旧実行の終了確認と成果保護を行い、
新規実行の許可・予算が既存承認に含まれるかを確認する。範囲追加だけを新規実行の許可としない。
発行済み指示・生の提出・旧結果 hash は変更せず、新契約と証拠を追記して関連付ける。

低速出力は活動の観測であり、完了・品質合格の証拠ではない。提出待ちも承認済みの
工程予算と期限に含め、検証・レビュー枠を流用しない。原因が未特定でも、正式受理と
同一 candidate の全検証が成立すれば独立レビューへ進める。成立しなければ成果と未達工程を
保存して停止し、レビュー到達を保証しない。

実装は共通の判定処理を各入口から使用し、commit／snapshot、直接受理／自動 workflow、
初回／修正／後続で意味を変えない。CLI reference・ready・役割指示・schema・保存証拠・
Reviewer handoff の対応を同じ変更単位で確認する。旧契約は版付きで維持し、
仕様追補だけで現行の拒否条件を迂回しない。既存の evidence 識別子や hash の厳密照合を
一括で緩めず、機械的導出が可能な条件と真正性・権限の条件を個別に区別する。

新しい機能や拒否条件を追加する際は、承認範囲内で自律的に進めるか、既存情報を先に使えるか、本当に新しい人間の判断が必要かを確認する。単に停止を避けるために検査を削る変更と、判断の重複をなくす変更を区別する。

直接関係する回帰試験には、許可済みの範囲で異なる手段を選んでも継続する例、権限や予算などを変えるため停止する例、失敗時も保存成果と不明点を維持する例を含める。特定のモデル応答文との完全一致を成果の合格条件にしない。新たな汎用評価基盤や全機能の一括改修を、個々の製品作業を再開する前提にはしない。

## 今回の実装：同じ判断を保存形式ごとに繰り返さない

`conversation confirm` は、完全な提案ハッシュと設定選択の正式確認を保存して Task を READY にする。一方、bundle-required graph では別の `task authorize` が必要だった。これは同じ契約判断の保存形式をつなぐための重複確認である。その正式確認を再利用し、モデルに自然言語の同義性や承認の有無を判定させない。

## 確認と承認束を同じ処理で保存する

bundle-required graph での `ConfirmIntake` は、READY への遷移と同じ transaction で、既存の compose・verify・append 処理により canonicalization version 2 の ApprovalBundle を導出する。提案ハッシュは元の確認要求、recordHash と7次元は確認後の完全な契約と選択設定を参照する。承認者・出典・理由・時刻は元の正式確認を保持する。途中で保存に失敗すれば READY 化や先行 Task の置換も取り消す。

旧版で確認済みの Task は、保存済みの完全一致する確認要求を再実行できる。不足束の導出には、元の DRAFT hash、最初の READY 履歴と現在契約の一致、設定承認、Flow・Graph／ledger Dispatch の不在を要求する。競合束や未知の schema は拒否する。束以外の Task・履歴・予算・期限・実行記録は変更しない。元の確認がなければ推測で復元せず、従来の明示承認経路を使う。

導出済みの束がある実行開始後の完全一致する再送も、元の READY 契約への束を検証し、新しい記録を作らずに処理する。これは現在の Task に再び実行許可を与える操作ではない。現在の契約や停止状態を検査する実行入口は引き続き必要である。

正式確認から導出済みの束を `task authorize` で読み戻す場合も、同じ契約・提案・設定を確認し、保存済みの承認者と出典を保持する。呼出し担当が変わったことだけで同じ承認を求めない。旧形式の graph は marker を変更せず、従来の意味を保つ。

## 役割委譲は既存の許可を先に調べる

束の生成は役割委譲や Flow 開始ではない。ただし、正式確認の `additionalTaskIds` が bounded Reviewer の設定をすでに対象としていれば、通常の Flow に新たな packet lifecycle 承認を必須としない。この既存経路を利用し、出典連鎖機能の選択とレビュー自体の実行許可を混同しない。packet lifecycle を選択するときの明示承認や、Flow の外枠・実行前検査は省略しない。

## 実行担当と操作担当の分離

柔軟な対応は、実装担当がTaxion操作担当へ切り替わることを意味しない。Dispatch の実装・レビュー指示は、外側の操作者向け方針より具体的な担当範囲を示し、管理 skill や管理状態の調査を製品作業の前提にしない。Copilot の実装・レビュー session では SDK の同名 skill 除外を使い、製品の skill と既存権限は維持する。管理 skill 自体にも、Dispatch 担当は管理手順を実行しない旨を明記する。

管理情報への読取り拒否を解消するためだけに権限や shell を広げない。controller 検証待ちと実装不能を区別し、必要な製品情報が不足する場合は具体的な未達要件を返す。除外設定と指示の試験は実モデルによる役割遵守の保証ではなく、配布前の設定・指示の回帰確認である。停止済み Flow の再送や課金不明の解消は含めない。

## 移行と旧版へ戻す手順

新しい DB schema や承認版は追加しない。旧記録は書き換えず、既存の承認束形式だけを追記する。旧版で読めても、正式確認時の自動導出と重複確認の削減はこの変更を含む版だけの動作である。旧版へ戻しても承認束や成果を削除しない。管理スキルは1.3.7へ更新するが、利用者の設置済みスキルを開発処理から変更しない。担当の管理 skill 除外と新しい指示は session hash に反映し、既存 session の再接続条件は書き換えない。

## 検証と残る実装

2026-10-27 に `go build ./...`、`go vet ./...`、`go test ./...` と変更に関係する controller／CLI の race 試験を実施した。独立した読取り専用コードレビューで重大な指摘はなかった。

回帰試験では、正式確認から全実行入口で利用できる束の導出、再実行の冪等性、旧形式の維持、不足束のみの追記、契約・設定・状態・履歴の不一致、既存 Flow／Dispatch、競合束、保存失敗の全体取消を確認した。承認済みの Reviewer 設定を持つ Flow が、追加の packet lifecycle 承認なしで開始と設定事前検査を通ることも確認した。CLI は別接続で導出済みの束を読み戻し、再承認や出典の変更がないことを確認した。実モデル呼出しによる評価や、製品の作業完了を示すものではない。

担当分離の変更でも build・vet・全試験と Copilot／CLI の関連 race 試験を実施した。新規接続・再接続と固定 ToolPolicy の除外、他担当・製品 skill の維持、旧 session hash との差、製品ファイルの読取り、管理情報・shell・未承認書込みの拒否を確認した。独立レビューで指摘された固定資産の診断表示は、内容の固定と実際の有効化を区別する `pinned-content` に修正し、回帰試験を追加した。実際の製品環境への導入・再実行は行っていない。

Issue #196 の全機能が完成したとはしない。実行外枠と内部遷移の承認整理、Copilot・OpenCode の互換更新、自動取得・切替、旧セッション／新セッションの継続判断は後続段階に残す。既存の hash 検証、設定検査、期限、課金、不明な配送、停止後の人間の判断を一括解除する変更は含めない。
