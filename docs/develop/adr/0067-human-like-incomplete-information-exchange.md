# ADR-0067: 不完全な情報を受け手が判断し、人のように情報交換して仕事を進める

Date: 2026-11-12

## Status

Accepted

## Context

これまでのエージェント間連携では、情報の不足や固定 schema の未充足を Controller 側で検出し、受け渡し拒否・停止へ結び付ける設計が強くなりすぎていた。
しかし、人の仕事では、受け手は不完全な依頼や途中の成果を受け取っても、まず内容を理解し、自分の知識と状況から判断する。判断できる範囲は進め、必要な点だけを質問し、回答を受けて仕事を続ける。可逆な仮定を置いて先に進む場合もある。

Taxion は完全な情報を要求するための検証装置ではなく、不完全な担当者同士でも相談・補完・判断を通じて成果を出すための道具である。形式的な完全性を優先して利用可能な仕事まで拒絶することは、この目的に反する。

## Decision

### 最上位の判断原則

エージェント間の情報交換と仕事の進行では、**情報が不足していることだけを理由に受け渡しや Job を拒絶しない。情報を受け取った Role が内容を理解して判断し、必要な場合に限って質問する。**

この原則は、Role 間の情報交換、Job 引継ぎ、Clarification、成果受入れ、レビュー、Controller の進行判断に関する設計・実装・Issue の上位判断基準とする。
既存 ADR の固定 schema、必須項目、blocked / reject の解釈がこの原則と衝突する場合、権限・安全・データ整合性を守る範囲で本 ADR を優先する。既存の承認・認可・セキュリティ境界を緩和するものではない。

### 受け手を中心にした情報交換

1. 受け手は、受信した自然言語、部分的な説明、既存 Context、成果物、証拠を使って、まず自分で判断する。
2. 判断可能な範囲は、明示した仮定や不確実性を必要に応じて添えて進める。
3. 判断に必要な情報が本当に不足している場合だけ、質問する。質問は作業を止めるためではなく、作業を成立させるために使う。
4. 回答を受けたら、元の Job・対象・担当関係に結び付けて反映し、仕事を続ける。
5. 受け手は、すでに Context や既存記録から分かることを聞き直さない。固定 schema の全項目を質問で埋めることを要求しない。
6. 仮定が可逆で影響が小さい場合は、仮定と影響を短く示して進めてよい。不可逆、重大、または権限に関わる判断は、既存の承認経路へ送る。

### Role ごとの判断責任

- Planner は、目的・背景・制約・未確定事項を実用的な Job として渡す。形式の完全性より、Coder が仕事を始められる理解可能性を優先する。
- Coder は、情報不足だけで作業を拒絶せず、実装可能な範囲を判断する。必要なら Planner 等へ質問し、回答または明示した仮定を反映する。
- Reviewer は、Coder の実成果・変更理由・検証証拠・未解決事項を基に独立して評価する。出力 schema の充足だけで成果の品質を代替しない。不足が評価を妨げる場合は、具体的な不足を質問または指摘する。
- Controller は、情報の完全性を一律に審査して Role の判断を代行しない。Job の同一性、進行、記録、権限、承認、安全性を管理し、Role が判断できる情報を渡す。

### 拒絶・停止を許す境界

情報不足と実行禁止を区別する。次の条件は引き続き fail-closed とし、Role の判断や自然言語回答で迂回しない。

- 認証・権限・秘密情報・禁止操作に関する違反または不明確さ
- 人間の承認が必要な操作、承認範囲・対象・予算・期限の実質的変更
- Job / Task / Dispatch / 成果物の同一性や出所を安全に確認できない場合
- データ破損、二重実行、競合する実行、不可逆な副作用の危険
- 実行状態が不明で、安全に再開・再送できない場合

これら以外の通常の説明不足、任意 metadata の欠落、自然言語の表現差、未確定の実装詳細は、それだけで拒絶理由にしない。受け手が判断できない場合は質問・保留・人間への相談を選び、理由と次の行動を具体的に示す。

### 実用性と改善

完全な自動協調や全ケースの保証を実装開始・利用開始の前提にしない。利用可能な最小経路を成立させ、既存テストで基本動作と安全境界を確認し、利用しながら問題を改善する。未対応範囲・既知の欠点・人間の介入箇所は明示する。
テストは安全に改善するための手段であり、未確認の仮説や網羅性を理由に実用的な機能の提供を無期限に止める条件ではない。

## Consequences

- Role 間の受け渡しは、固定 schema の完全充足ではなく、受け手が理解・判断して仕事を進められることを中心に設計する。
- Clarification は必須項目の収集機構ではなく、受け手が必要と判断したときの自然な相談手段とする。
- Controller の検証は安全性・権限・同一性・状態整合性に集中し、意味的な判断は担当 Role と独立 Reviewer に委ねる。
- Issue は本 ADR を判断基準として参照し、情報不足を理由とする拒絶を受入れ条件にしない。
- 実モデルで未確認の動作は未確認と明記するが、それを理由に実用可能な部分まで停止しない。

## Relationship to existing ADRs

本 ADR は、Role 間の情報交換と仕事の進行に関する上位判断基準である。

- ADR-0024 の利用者による質問・補足・本流への反映を、Role 間でも受け手中心の情報交換として適用する。
- ADR-0043 の承認 Gate、認可、read-only lane、権限・安全境界は維持する。固定 schema や情報完全性の解釈が通常の Role 間連携を不必要に拒絶する場合は、本 ADR に従って見直す。
- ADR-0066 の観測・受入れ・実行許可の分離は維持する。受入れ判定は安全・同一性・実行可否を守るために使い、意味情報の不足を一律拒絶するために使わない。
