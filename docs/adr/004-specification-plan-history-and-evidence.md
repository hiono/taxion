# ADR-004: 現行仕様・開発計画・履歴・検証証拠の正本を分離する

Date: 2026-11-20

## Status

Accepted

## Source decision

アーカイブ済み hiono/obsolete-taxion の redesign/job-centered-role-collaboration branch にある旧ADR-0085を原典とする（blob bd25f6aee937ecd3a61cf7a2298aceefec281055）。設計仕様、開発履歴、Issue / PR、CI証拠の責務分離を確認し、新しい履歴へ再確立した。特定の外部サービス、フォルダー、ファイルを恒久的な計画正本として固定しない。

## Context

ADR、現行実装仕様、開発計画、作業経過、CI結果を同じ文書へ蓄積すると、過去の実装状態や検証結果が現HEADの仕様・品質を保証するように誤読されます。情報の意味と更新頻度に応じて正本を分離し、保存先ごとの責務を明確にする必要があります。

## Decision

ADR-000で定める文書体系に従い、情報の種類ごとに現行の正本と記録先を分離します。次の対応を適用します。

| 情報 | 正本・保存先 |
| --- | --- |
| 現在採用している設計判断 | RepositoryのADR |
| 現在の実装仕様・操作方法 | Repositoryの現行ドキュメント |
| 設計・実装の変更履歴 | Git commit |
| TODO・ロードマップ・開発計画・実験計画 | 作業開始時に所在・アクセス権・更新時点を確認できた計画情報。特定の保存先を恒久的な正本に指定しない |
| 作業経過・未達事項・判断経緯 | GitHub IssueのNote / comment |
| 変更差分・レビュー・PR状態 | GitHub Pull Request |
| CI・配布・テストの実行結果 | GitHub Actions等の実行記録 |

### 1. ADRと現行仕様

ADRの作成・改訂・置換、文書体系および規範性はADR-000に従います。Accepted ADRは現行設計判断の正本です。製品仕様とテスト仕様は、それぞれ現在の製品契約と再現可能な受入条件を定義し、ADRの判断を暗黙に変更しません。

### 2. Repositoryの現行ドキュメント

Repositoryのドキュメントは現HEADのコードと設計に一致する現在の仕様・構造・操作方法を説明します。開発履歴、作業ログ、過去HEADの検証結果、時点依存の進捗記録を蓄積しません。

現行実装の利用に必要な再現可能な手順、test specification、API契約は記載できます。過去の実行結果を現行仕様の根拠として転記しません。

### 3. 可変計画情報の取得と有効性

TODO、ロードマップ、開発計画、実験計画は更新頻度の高い可変情報とします。特定の外部サービス、アカウント、フォルダー、文書名、URL、ローカルファイルを恒久的な正本としてADRや現行仕様へ固定しません。保存先や運用方法はプロジェクト運用に応じて変更可能とし、その変更を製品設計の変更として扱いません。

作業開始時には、現在アクセス可能な計画情報の所在、取得時点、更新時点、対象プロジェクトとの対応を確認します。外部文書への参照は、その時点で実際に取得・確認できた場合に限り有効です。ファイル名、過去のURL、会話履歴、キャッシュ、以前の取得結果だけでは、現在の存在・内容・アクセス権を保証しません。

計画情報を取得できない場合は「未取得・未確認」と明示します。過去の記憶や古い内容から現在のTODO・優先順位・進捗を推測して実行しません。計画が不在でも、Accepted ADRと現行コードから確定できる独立した作業は継続できますが、計画に依存する判断は保留します。

可変計画情報をGitへ無条件に複製して二重管理しません。作業上必要な決定は、製品仕様・設計判断に属するものだけをADRまたは現行仕様へ反映します。進捗・一時的なTODO・実験ログは、現在確認できる適切な運用記録先に保持し、その保存先が利用可能であることを確認してから記録します。

### 4. Git commit、Issue、Pull Request

- Git commitは設計・実装・現行ドキュメントの変更履歴を保持します。
- Issueは作業の時系列記録、未達事項、調査結果、判断経緯、次の作業単位を保持します。
- PRは変更差分、レビュー、修正、マージ判断の記録を保持します。
- 進捗や検証結果をRepositoryの現行仕様文書へ複製しません。
- Issue / PRのNoteには、対象HEAD、実施内容、検査結果、未確認事項を明記します。

### 5. CI・配布・テスト証拠

GitHub Actions等の実行記録を実行結果の正本とします。Issue / PRに結果を記載する場合はRun ID、検証対象の完全なHEAD SHA、workflow名、結果を対応付けます。

CI結果はそのRunが実際に検証したSHAにのみ有効です。後続commitでHEADが更新された場合、以前の成功結果を新しいHEADの検証結果として扱いません。未実施のテスト・Provider実行・配布検証を成功扱いしません。

## Alternatives considered

- **特定の外部サービスやファイルを計画情報の恒久的な正本にする:** 将来の存在・アクセス可能性・更新状態を保証できないため採用しません。
- **可変計画をADRへ固定する:** 計画変更を製品設計判断と混同するため採用しません。
- **進捗・CI結果を現行仕様文書へ複製する:** 対象HEADと説明対象の対応を失うため採用しません。
- **取得できない計画情報を過去の会話やキャッシュで補完する:** 現在の所在・内容・優先順位を誤認するため採用しません。
## Consequences

- 現行仕様文書は現HEADに同期し、過去の進捗やCI結果を含みません。
- 可変計画情報の保存先を固定せず、作業開始時の取得可能性と有効性を確認します。
- 過去の検証結果を現HEADの保証として扱いません。
- 過去に参照した外部文書が現在も存在するとは仮定せず、取得できない計画情報を推測で補完しません。

## Acceptance criteria

- ADR、製品仕様、テスト仕様、開発運用文書、可変計画、Git履歴、Issue / PR、CI証拠の責務を分離します。
- 可変計画の所在・アクセス可能性・更新時点を作業開始時に確認し、特定サービスやファイルを恒久的な正本に固定しません。
- 取得不能な計画情報は未取得・未確認とし、依存する判断を推測で実行しません。
- CI結果は実際に検証した完全なHEAD SHAにだけ対応付けます。
- 旧リポジトリの履歴・Issue・PR・コメントは読み取り専用とし、新しい判断は新Taxionへ記録します。
## Relationship to other ADRs

- ADR-100は製品目的を定義します。
- ADR-101は全体再構築原則を定義します。
- ADR-201〜0008は現在のドメイン・権限・通信・並行性の設計判断を定義します。
- 本ADRはADR-000の文書統治原則に従い、現行仕様、可変計画、Git履歴、Issue / PR、CI証拠の具体的な保存・更新規則を定義します。
