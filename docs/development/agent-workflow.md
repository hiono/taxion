# Development Agent Workflow

Version: 1.0
Date: 2026-11-20

本書はTaxionの調査・設計・実装・検証を継続する開発エージェントの作業手順を定義する。製品の設計判断はADR、現行動作は製品仕様、受入条件はテスト仕様に従う。本書は製品仕様を変更せず、開発作業の進め方を定義する。

## 1. 基本方針

- 目的は計画書や調査報告の作成ではなく、Taxionの製品価値を実現する変更を完了させることとする。
- 完璧さより実用性を優先する。ただし認証・認可・秘密情報・データ整合性は妥協しない。
- 利用可能な機能を、未完成機能の存在だけを理由に停止させない。
- 計画や説明だけで作業を終了せず、実行していない作業を実施済みと報告しない。
- 意味論的にまとまった単位で実装、テスト、Commit、Pushする。
- 通常の調査、設計、実装、テスト、修正、Commit、Push、CI確認は自律的に進める。人の判断が必要な重大事項のみ停止点とする。

## 2. 作業開始時の確認

作業開始時には次を確認する。

1. 開発対象が `hiono/taxion` であること。
2. 現在のbranch、HEAD SHA、差分、PR状態。
3. 関連Issueとコメント、Accepted ADR、製品仕様、テスト仕様。
4. 現行コード、関連テスト、CI実行結果。
5. 現在利用可能な計画情報の所在、アクセス可能性、更新時点。

旧 `hiono/obsolete-taxion` と `hiono/obsolete-taxion-poc` は読み取り専用の歴史資料とする。旧リポジトリへCommit、Push、Issue / PR / commentの変更を行わない。旧コードや旧履歴を新リポジトリへ無条件に移植しない。

計画情報の所在を特定サービスやファイルへ固定しない。現在取得できない計画は未取得・未確認として扱い、会話履歴や古い参照先から現行TODOを推測しない。Accepted ADRと現行コードから独立して確定できる作業は継続する。

## 3. 作業の選択

優先順位は次を基本とする。

1. 認証・認可・秘密情報・データ整合性に関する重大な問題
2. Accepted ADRに反する旧実行経路や不要な互換経路の除去
3. 第一段階のJob完遂シナリオを阻害する問題
4. Job-native実行経路の再構築
5. 利用可能な最小実用機能の不足

各作業単位について、目的、対象、完了条件、テスト方法、関連ADRを明確にする。コード変更前にADRとの整合性と旧設計由来の制約が混入しないことを確認する。

## 4. 開発ループ

1. 現状と一次情報を確認する。
2. 意味論的にまとまった作業単位を選択する。
3. 関連Issueへ作業方針と完了条件を記録する。
4. ADR・仕様に適合する実装を行う。
5. 対象テスト、回帰テスト、安全性関連テストを実行する。
6. 差分と影響範囲をレビューする。
7. [Development Quality Gates](quality-gates.md)に従い、Commit前の秘密情報検査を行う。
8. Commitを作成し、許可されたbranchへPushする。
9. GitHub上のbranch HEADとCommit SHAを照合する。
10. 対象HEADに対するCIを確認する。
11. Issueへ対象SHA、実施内容、検査結果、未確認事項を記録する。
12. 未達項目が残る場合は次の作業単位へ進む。

ローカルcheckoutがないこと、次の作業選択が必要なこと、テストやCIの失敗を、それだけで作業停止の理由にしない。利用可能なリモート手段を調査し、失敗は修正して再検証する。

## 5. Commit規則

- 新しい独立した意味的変更は通常Commitとする。
- 既存の意味的変更に対するバグ修正、CI修正、Fixture修正、import不足、既存実装の完成に必要な補正は、原則として対象Commitへの `fixup!` とする。
- フォーマットのみの変更は意味的変更と分離する。
- Fixup対象となる意味的Commitを特定できない場合は、推測でFixupを作成しない。
- autosquashや履歴書換えは、明示的な承認がない限り実施しない。
- 詳細なActions調査とFixup操作は[GitHub Actions and Fixup Runbook](github-actions-and-fixup.md)に従う。

## 6. 停止条件

次の場合に限り作業を停止する。

1. 定義した完了条件を満たした。
2. 必要な作業が完了し、利用可能な状態になった。
3. 利用者から明示的な停止指示があった。
4. 権限・認証・安全性の理由で継続が許されない。
5. 利用可能な代替手段を試しても、実行環境の制約で継続できない。
6. 人の判断が必要な重大事項が発生した。

調査結果や計画の作成だけを作業完了としない。

## 7. 作業完了報告

Commit / Pushを伴う作業では、次を報告する。

- Repository / Branch
- 変更概要
- Commit SHA、Commit種別（normal / fixup!）、Fixup対象
- Push先、Push結果、Remote SHA、SHA一致
- Secret scan結果
- 実施したテストとLinux / Windows / GoReleaser / macOS nativeの結果
- 対象HEADに対するCI結果
- Issueへの記録
- 未解決事項
- 次の作業

未確認の項目は「未確認」と記載する。実施していない検査や検証を成功扱いしない。
