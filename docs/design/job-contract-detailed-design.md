# Job Contract Detailed Design

## 1. Domain model

`Job` owns two append-only collections:

- `JobContractRevisions []JobContractRevision`
- `JobApprovals []JobApproval`

`JobState` supports `DRAFT` and `ACTIVE`. A new draft Job starts in DRAFT. Approval of the latest contract revision changes the state to ACTIVE. Contract proposals require a DRAFT Job, an accepted Taskless PLANNER Start, and a PlanningAuthorization that is still within its deadline. ACTIVE amendments are rejected until a separate authorized revision command is implemented; that future command must return the Job to DRAFT and require reapproval.

### 1.1 JobContract

```go
type JobContract struct {
    Purpose                 string
    Constraints             []string
    TargetRepositories      []string
    TargetResources         []string
    Workspaces              []string
    AcceptanceCriteria      []string
    RequiredEvidence        []string
    Budget                  JobContractBudget
    ConcurrencyCeiling      uint32
    Deadline                time.Time
    ProhibitedEffects       []string
    ApprovalRequiredEffects []string
    ConfigurationSHA256     string
}

type JobContractBudget struct {
    MaxTurns  uint32
    MaxTokens uint64
}
```

All list fields are set-valued: trim entries, reject empty / invalid UTF-8 entries and duplicates, then sort lexicographically. Purpose is trimmed and required. At least one target repository or target resource and at least one workspace are required. Acceptance criteria and required evidence must be non-empty. Budget limits and concurrency ceiling must be positive. Deadline must be in the future at proposal time. ConfigurationSHA256 must be a valid SHA-256 digest.

### 1.2 JobContractRevision

Fields:

- ID derived from CommandID
- CommandID and JobID
- monotonically increasing Revision
- CanonicalizationVersion
- CanonicalHash
- canonical JobContract
- Origin: `PLANNER` or `HUMAN_AMENDMENT`
- Planner origin: ProposedByRoleExecutionID, SourceResultObservationID, SourceResultContentSHA256
- Human amendment origin: AmendedByPrincipalID, AmendedByIssuer, AmendedBySubject, AmendmentReason, SupersedesRevision, SupersedesCanonicalHash
- CreatedAt and CreatedRevision

For `PLANNER` origin, the proposer must be a Taskless PLANNER RoleExecution belonging to the same Job, with an accepted Provider Start and a PlanningAuthorization valid at CreatedAt. The source Result must be a persisted final ProviderResultObservation in the same Job, produced by that exact RoleExecution, and its ID and ContentSHA256 must match the revision provenance. The Result observation's own validation must bind it to the accepted Start / Session and exact Turn. Human amendment fields must be empty.

For `HUMAN_AMENDMENT` origin, Planner RoleExecution / Result provenance fields must be empty. The revision records the authenticated HUMAN Principal's ID / issuer / subject, a non-empty reason, and the exact prior approved revision / canonical hash. The Principal's authentication timestamp must be at or after the prior JobApproval time. The prior revision must be the latest JobContractRevision and have a matching JobApproval. The new revision is appended while the Job transitions from ACTIVE to DRAFT; prior approvals remain historical. The canonical contract hash and source Result content digest are separate identities and must never be substituted for one another.

### 1.3 JobApproval

Fields:

- ID derived from CommandID
- CommandID and JobID
- ContractRevision, CanonicalizationVersion, CanonicalHash
- ApproverPrincipalID
- ApproverSource (authenticated OIDC issuer)
- ApproverSubject
- Reason
- ApprovedAt and CreatedRevision

The Principal must validate and have a `human_` Principal ID. ApproverPrincipalID must equal the identity derived from ApproverSource and ApproverSubject. Reason is required, valid UTF-8, and at most 2,000 bytes. Approval time is generated by the Store, not supplied by the caller.

## 2. Canonicalization

Canonicalization version 1:

1. Validate required scalar values and trim surrounding whitespace.
2. Normalize all set-valued string slices by trimming, rejecting empty / duplicate entries, and sorting lexicographically.
3. Normalize Deadline to UTC and remove monotonic clock data.
4. Serialize a fixed-order struct containing the canonicalization version and canonical JobContract using `encoding/json`. No maps are permitted in the canonical representation.
5. Compute lowercase hexadecimal SHA-256 over the serialized bytes.

The version is part of the hash preimage. Any canonicalization rule change requires a new version; historical hashes are never recomputed under a newer version.

## 3. Domain invariants

- Contract revision numbers are contiguous, unique, and append-only.
- Every revision hash recomputes exactly from its stored canonical content and version.
- Every revision references a PLANNER RoleExecution in the same Job.
- Every revision references an existing final ProviderResultObservation in the same Job and same RoleExecution; the stored Result ID and content digest must match exactly.
- The source Result must validate against the accepted Provider Start / Session and exact Turn identity.
- At most one JobApproval exists per contract revision.
- Every approval binds the exact revision, canonicalization version, and canonical hash.
- Approver identity is a validated HUMAN Principal and source is its authenticated issuer.
- ACTIVE requires an approval for the latest contract revision.
- DRAFT must not have an approval for its latest revision.
- A new revision on ACTIVE changes state to DRAFT; prior approvals remain historical.
- JobApproval does not replace PlanningAuthorization or ExecutionPermission.

## 4. Store commands

### 4.1 AddJobContractRevision

Input: Job ID, expected Job revision, CommandID, Planner RoleExecution ID, exact source Result observation ID, source Result content SHA-256, and JobContract.

The Store creates the next immutable contract revision only for a DRAFT Job while the referenced PlanningAuthorization remains valid. In the same aggregate transaction, it resolves the source Result observation by ID and verifies its JobID, RoleExecutionID, Final flag, ContentSHA256, accepted Start / Session / Turn binding, and full Domain validity. A missing or mismatched Result fails closed. The command is idempotent by CommandID and canonical request hash, including all source provenance fields. ACTIVE amendments are rejected until a separate authorized revision command exists.

### 4.2 AddJobApproval

Input: Job ID, expected Job revision, CommandID, exact contract revision / hash / canonicalization version, reason, authenticated HUMAN Principal.

The Store verifies that the target is the latest revision, creates the approval fact, and transitions the Job to ACTIVE atomically. Duplicate approval of the same revision is rejected; replay of the same CommandID returns the original receipt and fact.

### 4.3 AmendJobContract

Input: Job ID, expected Job revision, CommandID, exact current approved contract revision / canonical hash, reason, replacement JobContract, and authenticated HUMAN Principal.

The Store accepts this command only for an ACTIVE Job whose latest revision has a matching JobApproval and whose revision / hash equal the supplied base. It appends a new immutable `HUMAN_AMENDMENT` revision, updates the Job goal, and transitions the Job to DRAFT in the same aggregate transaction. The prior JobApproval remains historical and does not authorize the new revision. The new revision must receive a new JobApproval before activation. A replay with the same CommandID and identical base / reason / contract / Principal returns the original receipt; changed input conflicts.

The amendment command does not create ExecutionPermission, start a Provider operation, or authorize any agent execution.

All commands use the shared aggregate transaction: expected-revision check, idempotency receipt, append-only fact, aggregate validation, atomic update, and read-back on retry.

## 5. Execution boundary

This design establishes JobContract / JobApproval Domain and Store facts plus proposal / approval Controllers. Provider execution remains blocked until a separate execution Controller verifies the current approval and creates an explicit ExecutionPermission bound to the approved contract. Do not add a placeholder approval boolean or infer authority from Job state alone.

## 6. Planner proposal Controller

The Controller accepts a proposal only from a validated AuthenticatedPrincipal whose identity matches the PlanningAuthorization bound to the referenced RoleExecution. The RoleExecution must be a Taskless PLANNER in the same Job, the Job must be DRAFT, and an ACCEPTED Provider Start observation must exist for that execution.

The Controller requires the exact persisted final Result observation ID. It verifies that the observation belongs to the same Job and RoleExecution, and that its accepted Session / Turn provenance is valid. The Controller passes the Result ID and content digest to the Store command. The Store repeats these checks inside the aggregate transaction; Controller preflight alone is not the integrity boundary.

For a new proposal, the Controller revalidates the current PlanningAuthorization and its deadline immediately before calling the Store. The Store remains the authoritative mutation boundary: it validates the accepted Start, source Result provenance, canonical contract, deadline, expected Job revision, idempotency identity, and aggregate invariants in one transaction.

The Controller does not call the Provider, change Job authority, issue JobApproval, or create ExecutionPermission. A committed proposal may be retried after the PlanningAuthorization deadline only with the same CommandID, identical canonical request, and identical source Result provenance; the Store returns the original receipt and fact. A different Result ID / digest, payload, or proposer with the same CommandID is rejected as an idempotency conflict.

### 6.1 Planner Result payload decoding

The Planner's final Result content is exactly one JSON object representing `JobContract`. JSON keys use the struct's lower_snake_case tags; `budget` is a nested object with `max_turns` and `max_tokens`. The object contains no wrapper, Markdown fence, explanatory prose, or trailing value.

The proposal Controller receives only the persisted Result observation ID. It loads the JobAggregate, resolves the exact final Result, validates its Job / RoleExecution / accepted Start / Session / Turn provenance, and decodes the Result content into JobContract. It does not accept a parallel caller-supplied JobContract value. The Planner workflow entrypoint is `PlanningController.ProposeJobContract`, which delegates to `JobContractController.Propose` and accepts only the Job / RoleExecution / Result observation / Command identities plus the authenticated Principal.

Decoding rejects:
- non-object roots and malformed JSON;
- unknown keys or keys with non-canonical casing;
- duplicate keys at the root or nested `budget` object;
- non-JSON prefixes / suffixes, Markdown fences, or multiple JSON values;
- type mismatches and values that fail JobContract canonicalization.

Duplicate-key detection runs before struct decoding because the standard Go JSON decoder otherwise accepts duplicate object keys. The decoded contract then passes the existing canonicalization v1 and Domain validation. The source Result digest remains separate from the canonical JobContract hash.

## 7. Human approval Controller and CLI ingress

The approval command is an explicit human action. The CLI displays the persisted JobContract through the existing Job read command; the caller then supplies the exact Job ID, revision number, canonical hash, canonicalization version, and reason. The CLI must not infer the revision or hash, approve a proposal from Planner output alone, or treat a natural-language confirmation outside the authenticated command as approval.

The CLI authenticates through the existing OIDC Authorization Code Flow with PKCE before opening the Job Store. It passes only the resulting AuthenticatedPrincipal to JobContractController. The Controller verifies the exact latest revision binding and calls AddJobApproval with the current expected Job revision. The Store generates ApprovedAt and atomically appends JobApproval and transitions DRAFT to ACTIVE.

The same CommandID and identical approval request may be retried after the transition to ACTIVE and must return the original receipt. Reusing the CommandID with a different Principal or payload is an idempotency conflict. A new approval command for an already approved revision is rejected.

The approval path does not create ExecutionPermission or start a Provider operation. Execution remains blocked until a separate Controller verifies current JobApproval, approved scope, budget, deadline, Provider identity, resource boundary, and prohibited effects.

### 7.1 ACTIVE Job amendment CLI ingress

`taxion job amend` requires explicit `--revision`, `--canonical-hash`, `--reason`, and `--contract-file` values. The contract file is limited to 1 MiB of UTF-8 and must contain exactly one strict JobContract JSON object. The CLI authenticates through OIDC Authorization Code Flow with PKCE before opening the Job Store, then calls JobContractController.AmendJSON with the current expected Job revision.

The command appends a `HUMAN_AMENDMENT` revision and returns the Job to DRAFT. It does not approve the new revision; a separate `taxion job approve` command must approve its exact revision / canonical hash. The same CommandID and identical base revision / hash, reason, contract, and Principal identity may be retried after the Job transitions or is reapproved. Authentication timestamp is retained in the original revision but is not part of the idempotency payload, allowing the same human to reauthenticate for a retry.

The amendment path does not create ExecutionPermission or start a Provider operation.
