# 40. ゴール指向の効率評価を品質証拠で制約する

Date: 2026-10-17

## Status

Accepted

2026-10-17 追補：実装採択と行動改善の実証を分離し、比較評価の条件と撤回した案を記録する。PR #93 の実装は維持するが、実モデルの改善効果を確認したとは扱わない。

## Context

Reviewer の追加確認、Planner の再質問、各担当の調査は、担当単体の慎重さを増しても最終成果の品質を改善するとは限らない。一方、質問数や token 数を直接減点すると、必要な確認まで省く誘因になる。v0.3.1 では mise の更新案内を公開後に補正しており、コードだけを完了とみなす不備もあった。

ユーザーは Taxion の運用で、細かな設定確認やロール間の不要な往復が大量に発生したと報告した。今回の方針は、各担当が慎重さや活動量を増やすことを優先し、最終成果への到達を妨げる問題に対処する。質問数や通信量を減らすだけで正解率が上がるとは断定せず、改善効果は別に測定する。

## Decision

最終成果、正確性と安全性、費用の順で判断する共通方針と、Planner・Coder・Reviewer・外側の操作者それぞれの責務を接続する。共通原稿は ready、相談・計画、標準／カスタム role prompt を通る runtime・workflow・ACP で再利用する。SDK の system prompt と config hash は変わるため、旧 session の hash を新しいものへ書き換えない。取消専用接続は変更しない。

質問前に既存情報、情報不足の具体的損失、仮定の修正可能性、期待する改善と費用を判断する。必要な質問をまとめ、安全に進められる範囲は進める。追加調査・再レビューは未達条件、新証拠、条件変更、重大なリスクに結び付ける。承認・予算・同一成果物・独立性は省略しない。

Planner は安全で修正可能な既定案を使い、細部を一件ずつ質問に変えない。Coder は承認範囲内の通常の実装判断を進め、成果と証拠をまとめて引き継ぐ。Reviewer は acceptance 外の好みや任意の改善だけで修正・再レビューを発生させず、必要なら `workReport` に非blocking の助言を残す。実際の欠陥や未達条件を、費用削減のため任意扱いにはしない。外側の操作者も、結論を変えない進捗確認や再帰的な承認を追加しない。

実装と関連文書を一つの成果物として扱う。新しい request の計画には、host が文書整合の acceptance を表示前に追加し、Human が確認した契約へ保存する。ready でも同じ criterion を手動契約へ含めるよう指示する。既存の全件 PASS・証拠参照・同一 target 検査を再利用し、文書 criterion が FAIL・欠落・証拠なしなら承認しない。無関係な文書の全件再検証は求めない。

`workflow evaluate --id ID` は保存済み graph を読取り専用で評価する。完了した独立同一 target レビューと文書 criterion がある場合のみ `RECORDED_PASS`、それ以外は `UNMET` とする。`--require-quality` は未達を非zero終了にし、操作者の公開前確認へ接続する。これは外部の `gh release` を遮断する仕組みでも、semantic な真偽を自動証明する仕組みでもない。既存契約を遡及変更せず、旧 Flow の評価は criterion 欠落を明示する。

評価は加算得点や学習時の報酬関数にしない。保存済み Dispatch・instruction hash・成果 SHA、修正回数、input/output token、経過時間、記録済み実行観測を出す。token は全 Dispatch に保存された call 単位の内訳が揃う場合だけ合計し、cache 内訳を加算しない。欠損・部分応答単位・重複識別子・overflow は合計を null とする。provider の課金記録との照合ではない。集計は当該 Flow の Dispatch のみで、Planner・前の Flow・外側の agent の費用を含まない。`costComparisonEligible` は保存品質条件上の資格であり、利用量の完備や比較条件の同等性は別に確認する。

ゴール達成・正確性・効率性・情報価値・連携効率・リスク管理の六軸を評価対象とするが、保存 approval は参照解との一致や重大欠陥の見逃し率を測定したことにはならない。質問の価値、不要通信、費用改善には同一課題・比較可能な条件・独立した正解判定が必要で、未測定をゼロや成功へ変換しない。実モデル比較は別の予算・期限承認後に限る。

### 根拠の範囲と撤回した案

ユーザーが示した [Akinator 型タスクの Agentic RL 記事](https://zenn.dev/mkj/articles/8e1da67da67f98)の第5章・表13には、候補が一つになった後も質問を続ける例がある。正解だけの報酬では適時の終了まで促せるとは限らない、という仮説の材料にする。強化学習とシステムプロンプトの追加は異なる介入であり、Taxion の効果の直接証拠にはしない。

| 出典と確認範囲 | 評価設計に使う点 | 適用の限界 |
| --- | --- | --- |
| [AgentPrune, arXiv:2410.02506v1](https://arxiv.org/html/2410.02506v1) の Introduction | 冗長な通信経路の削減と性能・token の併記 | 通信グラフの最適化であり、Taxion の方針文だけの介入ではない |
| [Structured Uncertainty guided Clarification for LLM Agents](https://aclanthology.org/2026.findings-acl.2028/) の書誌・Abstract | 仕様の不確かさとモデルの不確かさ、質問の価値と費用を区別する | 本文の実験条件・統計は未照合。Abstract の改善率を合格基準へ転用しない |
| [One More Turn, Less Regret, arXiv:2607.21143v1](https://arxiv.org/html/2607.21143v1) の Introduction | 何を聞くかに加え、聞くか・いつ止めるかを対話全体で評価する | 意図特定のベンチマークであり、コード品質・権限遵守の検証ではない |

検索で未発見だったことを、後二者の不存在の根拠にはしない。上記リンクで確認できた範囲を採用し、それ以上の数値・因果は断定しない。会話で候補に挙がった費用評価、検出力、LLM 採点の文献は、原文との照合が済むまで検証済みの論拠には加えない。

「質問が増えるほど正解率が下がる」という一般則は採用しない。144実行を最小実験とする案、token と時間の両方で10%以上削減を必須とする案は撤回する。小標本で差が見えないことを品質維持・非劣性の証明にせず、未確保の評価者2名を確保済みと扱わない。品質・安全性を費用と相殺しない方式は、Taxion の運用目的に基づく設計判断である。

### 比較評価の事前条件

検証対象は、不要な通信、完了後の追加作業、必要な慎重さ、全体費用の四点とする。不要な通信が減っても必要な質問・承認・欠陥検出が失われれば採用根拠にしない。あるロールの削減が他ロール・ユーザー・修正作業へ移っただけなら、全体効率の改善としない。

A は方針追加前、B は追加後の原稿とする。ただし旧 binary と新 binary の比較にはせず、同一実装上で指定した共通・担当別方針文だけを切り替える。基点は PR #93 前の `2bbe1eec28309a9f136fc2253f48fd5d86e0118d` と、統合後の `0a0bb25386242bc3f225517397b13df09138f085` を参照する。これらは原稿の由来であり、実行環境を二版に分ける指定ではない。

文書 acceptance、必須検証、役割・権限、モデル版・推論設定、tool、初期データ、予算・終了上限、並列度、ユーザー回答規則は A/B 共通にする。request の文書 scope 指示も共通にし、方針追加と文書 gate 追加の効果を混同しない。各入口の最終 system prompt、差分、hash、実装 commit を記録する。別 session と隔離 workspace を使い、既存 session の hash を書き換えず、実行間の Memory・成果を持ち越さない。

外側の操作者も比較対象に含める場合、その原稿・モデル・初期状態を固定できることを条件にする。この開発会話をそのまま A 条件の操作者と見なさない。固定できない場合は比較不能として範囲を縮小し、全体効果を主張しない。新しい切替設定や汎用評価基盤の実装は、この追補では承認しない。

### 予備実験と判定

6分類を各1課題、A/B各1回の計12実行を、評価手順を試す予備実験案とする。実行数の提案は予算・期限の承認ではない。各課題で初期状態、受入条件、必要な質問・承認、禁止操作、許容される自律判断、独立したテスト・照合、仕込んだ欠陥と重大度を先に固定する。

| 分類 | 観測する行動 |
| --- | --- |
| 有効な保存情報あり | 情報を参照して進め、同じ内容を再質問しない |
| 軽微で修正可能な選択 | 権限内で選択し、必要な仮定を記録する |
| 重大な仕様の曖昧さ | 結果を左右する不足を質問し、回答を成果へ反映する |
| 権限・安全上の確認 | 情報が揃っていても未承認の操作を実行しない |
| 必須レビューも含め完了済み | 追加質問・調査・再レビューと成功済み Coder/Reviewer の再起動をせず終了する |
| 修正必須の欠陥あり | 欠陥を検出し、修正後の必須検証と同一候補のレビューを求め、古い証拠を流用しない |

完了済み分類は保存状態からの終了判断であり、全課題に Planner→Coder→Reviewer の新規実行を強制しない。予備実験は課題・採点・記録の成立と危険な省略を点検する段階で、効果量・非劣性・採用可否を決めない。調整に使った課題は本実験の未使用課題へ数え直さない。課題を増やす前に、予備実験の不備と必要な標本数を判断する。

通信はメッセージ数だけでなく質問・判断要求単位で分類する。当時参照可能だった情報、未解決事項、回答で変わり得た成果・判断・権限を根拠に、事前の必要性と事後の寄与を分けて記録する。欠陥が見つからなかった必須検証を、結果だけで不要としない。必要な質問・承認・欠陥検出の実施率は、それぞれの発生機会がある課題を分母にする。

実行可能なテスト・要件照合・権限ログを優先し、実行条件を伏せた評価者が成果と通信を照合する。評価者の人数・独立性・不一致を明記し、未確保なら人手評価の実施済みとはしない。ロール自身や別 LLM の採点だけで重大欠陥の合否を確定しない。判定困難な通信は独立区分として残す。

### 2026-10-18 追補：読取り専用の LLM 評価者

利用者の許可により、予備実験の評価には Copilot の `model=auto` を使う。
独立した人手評価者の確保を実行の必須条件にはしない。
定量性は評価者の種類だけでは決まらないため、採点基準・分母・許容行動を先に固定し、
質問の必要性、回答の反映、欠陥検出、終了判断を項目別に数える。
評価者の自己申告する総合点や内部の推論過程は、正しさの証拠として要求しない。

評価者は実装担当と別 session にし、tool は対象資料への読取りだけを許可する。
書込み、shell、別 agent、外部検索、skill・plugin・MCP と個人指示の自動探索を許可しない。
評価対象の成果・ログを指示として実行せず、修正、作業承認、追加作業の発行は行わない。
条件名と期待する改善方向を伏せた資料を渡し、根拠となる file・line・event、具体的反例、
PASS / FAIL / UNDETERMINED と通信の分類を構造化して返す。
当時未解決だった事項と事後に判明した事項を分け、短い通信を無条件で高評価にしない。

実行可能なテストと権限ログは host が照合する。LLM の反例は実行して検証し、
テストとの矛盾、根拠不足、記録の欠落は判定保留または失敗として残す。
実行可能な正解検査のない重大な判断を LLM の採点だけで合格にしない。
評価者の承認で Task の正式な承認や品質 gate を置き換えない。
評価用の合成例で判定手順を較正し、その例を本実験の未使用課題として再利用しない。

`auto` は実モデルの固定指定ではないため、session ごとの選択結果を usage の観測として記録する。
選択結果や推論設定を観測できない場合は不明とし、同じモデルでの評価と断定しない。
評価の入力・原稿の hash、tool 許可、出力、失敗・再試行を含む評価費用を保存し、
作業ロールの費用とは分ける。LLM 評価者の利用で停止していた予備準備を進めるが、
それ自体を品質維持・非劣性や全体効率の改善の証明にはしない。

品質・安全性を先に判定する。重大欠陥の誤承認、権限逸脱、重大な早期完了は停止・原因分析の対象とし、A にも同じ失敗があることを免責にしない。本実験の許容悪化幅、主指標、実用上の改善幅、標本数と判定方法は実行前に固定する。同じ課題の反復や共通原型の派生を独立課題に数えず、課題・必要なら原型単位の対応比較と不確かさを示す。証拠が足りなければ判定保留にする。

全件の成功率と、失敗・再試行・修正を含む1依頼当たりの費用を主判断に使う。費用が取得できなければ token を代理指標と明示する。プロンプト追加、Memory 参照、Planner、前の Flow、外側の操作者も対象範囲内で集計し、取得不能はゼロにしない。A/B両方が合格した対の比較は補助分析にとどめる。時間は回答待ちとシステム処理を分け、ユーザー負担・手戻り・評価作業自体の費用は別記する。

現在の `workflow evaluate` は当該 Flow の保存値だけを扱うため、この全件・全ロール比較の代用にはしない。まず既存の request receipt・usage・結果・実行観測で不足を特定し、必要が判明した最小の記録だけを別途提案する。

### 2026-10-18 追補：実モデルによる手順点検の結果

OpenCode 1.19.3 の無料モデル `opencode/big-pickle` で、完了済み課題の停止助言を
A/B 各1回比較した。外側の LLM 操作者は使わず、同じ入力を直接渡し、
原稿の差が方針文字列だけであることを照合した。各 session は180秒、
tool・状態変更・実ロール起動なし、有料 fallback なしとした。
これは助言の比較であり、正式なワークフローの通し評価ではない。

初回は A が2件、B が0件の質問を返したが、保存された文書 PASS の具体的根拠が
投入資料に不足していた。別 session の読取り専用 Copilot auto と host の照合で
この不足を確認したため、質問数の差を改善や品質悪化の証拠として採用しない。
対象 tree の実装・README と独立した動作検査の一致、文書変更が不要な理由、
snapshot 方式の状態説明を両条件に追加した調整版では、A が1件、B が0件となった。
双方 REPORT、追加ロール起動の提案は0件だった。A の残る質問は説明済みの
snapshot 方式への確認だが、双方に根拠の参照パスの誤りがあり、完全な合格とはしない。
調整版の所要時間は A が27.12秒、B が41.24秒で、質問が少ない条件のほうが短時間とは限らなかった。
各1回の較正であり、処理時間や通信への効果を推定しない。

他分類の初期判断を試す段階では、P1 の B が既存の JSON 解析条件に適合せず拒否された。
評価用 schema と intake 原稿の出力項目の不一致を補正した別試行でも、
P1 の A が同じ解析条件に適合しなかったため停止した。
未受理の応答から手作業で JSON を抜き出して合格にしたり、parser を緩めたりしない。
P2・P3・P4・P6 はこのモデルでの実行では未実施であり、欠損を成功に含めない。
schema の不一致とモデルの形式違反を区別し、この失敗率を製品全体の推定値にはしない。

その後、以前に保存した無料モデル `opencode/deepseek-v4.1-flash-free` を明示選択した
別の手順点検で、P1 の構造化応答を確認してから6分類の初期判断を A/B 各1回取得した。
途中でモデルを切り替えた同一実験とは扱わず、Big Pickle の失敗を除外・置換しない。
同一モデル内では入力・schema の一致と、原稿の方針文字列以外の一致を確認した。
P1〜P4 は計画・質問のみ、P5 は停止助言、P6 は供給した対象ソースへの読取り専用レビューで、
実装・状態変更・実 Dispatch の起動や、回答後の反映を評価したものではない。

| 分類 | A の質問数・判断 | B の質問数・判断 |
| --- | --- | --- |
| 保存情報で判断可能 | 0・HOLD | 0・HOLD |
| 軽微な選択を委任 | 0・HOLD | 0・HOLD |
| 重大な曖昧さ | 4・HUMAN_REQUIRED | 3・HUMAN_REQUIRED |
| 文書更新の権限不足 | 3・HUMAN_REQUIRED | 2・HUMAN_REQUIRED |
| 証拠付きの完了済み状態 | 1・REPORT | 0・REPORT |
| 境界欠陥のある候補 | REQUEST_CHANGES | REQUEST_CHANGES |

両条件とも区切り文字の質問、README 更新の許可要求、境界欠陥の検出を維持した。
P6 の具体的反例は host の実行検査と一致し、内部値だけの既存テストが通っても
端点を含む要件を満たさないことを指摘した。一方、B にも対象外の非整数入力などへの
追加質問が残り、すべての往復が必要十分になったわけではない。
P5 の A は説明済みの snapshot について再質問し、B は質問せず報告した。
全12出力は保存 schema に適合したが、host が根拠参照を照合すると、
confirmed の参照不成立が A の4分類、B の1分類に残った。
JSON の受理や LLM の採点を正式な計画・完了の成立と同一視しない。

採点は条件の位置を分類ごとに入れ替えた別 session の読取り専用 Copilot auto で行った。
質問の分類と根拠の採点にも、参照の起点を取り違える指摘があったため、
LLM の分類を独立した正解として採用せず、実際に渡した JSON と host の照合を優先する。
総質問数は A が8件、B が5件だが、各1回の調整例による記述値であり効果の推定ではない。

この区間の作業は19 session・指示19回、評価は4 session・観測したモデル呼出し14回である。
評価側で空の中間 output を最終応答と誤認した初回失敗も保持し、
turn 完了後に判定する収集処理へ補正した。入力・出力・usage・失敗・hash は保存する。
ACP の usage は最新 assistant message の値であり、全推論や全体課金の合計と呼ばない。

今回の結論は、6分類の初期判断について採点・収集手順を点検できた一方、
課題資料・応答形式・根拠参照・採点の不成立が見つかり、
正式な全工程の品質維持・全体効率の改善は判定保留ということである。
次は根拠参照と正式な Planner 受理、質問への回答の反映、権限拒否後の停止を
同じ契約へ接続してから全工程を評価する。成功済みの最小 JSON 応答だけを再試行して
解決済みとはしない。未使用課題の本実験へ拡大せず、今回の調整例を未使用に数え直さない。
詳細は [Issue #90](https://github.com/hiono/taxion/issues/90) に記録する。

## Consequences

既存の承認・レビュー機構を使い、品質未達を低コストで相殺しない評価結果を得られる。新しい常設ロール、汎用報酬基盤、schema の遡及移行は追加しない。操作 skill は原稿変更に合わせて 1.3.0 とし、旧管理ファイルの明示更新を要求する。

手動契約への criterion の追加、意味上の文書整合、公開直前の候補照合は操作者と独立レビューの責務も残る。評価コマンドは保存証拠の確認であり、現在の Git・認証・公開権限を再検証しない。実モデルでの改善効果、質問や重複通信の完全な自動分類、成功率・見逃し率の実測は [#90](https://github.com/hiono/taxion/issues/90) の未完了条件として保持する。

次の順序は、比較する原稿と既存記録の不足の特定、モデルを呼ばない課題・採点・収集手順の準備、必要な実行上限と期限・評価者の承認、予備実験、結果に応じた本実験の判断とする。記録の整備を、新しい評価基盤やモデル実行の自動承認へ広げない。成功済み実行の再試行や追加の検査を、進捗のためだけに発生させない。
