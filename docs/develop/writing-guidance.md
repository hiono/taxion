# 文章指針と独立レビュー

公開文章に使う指針は、対象プロジェクトの読者と公開範囲に合うものを文章生成前に選びます。最終出力の検査だけで、指針の互換性を代替しません。

## プロジェクトと指針を照合する

`TAXION_COMMUNICATION_PROFILES` に、Forge、host、repository が完全一致する設定ファイルを指定します。設定は別プロジェクトから継承せず、文章の内容から自動推定しません。`configuration` が `fixture` の設定は試験用であり、本番投稿を許可しません。

各プロジェクトは `projectType`、主言語と許可する副言語、タイトルと本文の言語、想定読者、公開範囲、技術用語と用語集を定義します。非公開の製品プロジェクトを本番で使用する場合は、`titleStyle`、`issueStructure`、`mergeRequestStructure`、`confidentialIdentifierPolicy`、`releaseNoteLanguage`、`correctionPolicy` も明示します。実プロジェクトの値は、そのプロジェクトの承認済み設定として別途保存します。試験用の例を本番へ転用しません。

Taxion は `titleStyle: "plain-statement"` を指定します。この設定では、タイトルの先頭にあるコミット分類、工程番号、配布予定の版、将来の計画区分を共通の検査で拒否します。他プロジェクトへこの設定を自動継承しません。言語、内容、問題の理解に必要な識別子の妥当性は既存の検査と独立レビューで確認し、形式検査だけで意味の適合性を保証しません。設定変更後は以前の設定に対する承認を再利用せず、文章を再確認します。

`guidance` は識別子、想定読者、対応する公開範囲とプロジェクト種別、主言語と副言語、文書種別、用語の分野、公開適性、機密性の前提、指針本文を保持します。必須メタデータの欠落や不一致がある場合は本文を返しません。社内マニュアル専用の指針は公開OSSへ使用しません。一般的な文章品質規則を利用する場合も、公開OSS向けに分離した指針として登録します。

`go run ./scripts/publictext -guidance REQUEST.json` は、`provider`、`host`、`repository`、`documentType` を指定した要求から、互換性のある指針本文と `guidanceDigest`、`profileHash` を返します。先にこの選択を行ってから文章を作成し、正確な文章の要求へ `guidanceDigest` を含めます。指針を差し替えた場合、以前のダイジェストでは投稿できません。

Taxion の公開OSS用指針は `.github/communication-profiles.json` にあります。利用者、貢献者、保守者、セキュリティ調査者、配布物の利用者を対象とし、Issue、PR、レビューへの応答、Release Notes、README、利用ガイド、貢献ガイド、ADR、CLI ヘルプ、CI の説明に使用できます。事実と予定、安定した参照、言語の統一、利用者に見える動作の直接説明、内部証拠の分離、アクセシビリティと明瞭さを原則とします。

## 重要な文章は独立して意味を確認する

決定的な検査には意味や事実の判断に限界があります。`requireSemanticReview` を有効にしたプロジェクトでは、重要な新規文章について、作成とは別のレビューで次を確認します。

- 読者が問題、変更、利用者への影響、制約を理解できること。
- 内部の手続きではなく対象の動作を説明し、存在しない組織や役割を前提としないこと。
- 設定した言語と用語に従い、技術的識別子と自然言語を区別すること。
- 予定と確認済みの事実を区別し、参照先が記述時点で存在すること。

副言語の明示的な引用には `> [en] ...` または `> [ja] ...` を使用できます。その言語がプロジェクトの副言語として許可されている場合に限ります。識別子の引用はインラインコードを使用し、未許可の自然言語を隠す用途には使いません。

`-review-basis MUTATION.json` は正確な文章と設定のハッシュを出力します。Release Notes の確認には `-release-review-basis TAG` を使用します。どちらも承認や投稿は行いません。独立したレビューの結果を、本文、記述時点、参照先とその状態を含む `contentHash`、設定の `profileHash`、作成とレビューの異なる実行識別子、`APPROVE` の判断、結果の参照として `semanticReview` に付与します。本文、指針、設定、記述時点または参照の主張が変わった場合は再確認が必要です。

Release Notes の独立レビュー記録は `.github/release-semantic-review.json` に保存します。確認した `statement` もそのまま記録し、公開時に記述時点を自動更新しません。記録の欠落、本文、設定または参照の主張との不一致では公開できません。これは協調的な証跡の照合であり、レビュー者の暗号学的認証ではありません。信頼する設定と証跡を管理し、決定的な検査の成功から独立レビューの承認を自動生成しません。

## GitLab の既存文章を変更せず検査する

`-audit-gitlab REQUEST.json` は明示された本番設定、認証、保護対象一覧を使用して、Issue、MR、各コメントとレビュー記述、Release、milestone、label の文章を読取り専用で取得します。`-audit-file REQUEST.json` は、`recordsFile` で指定した JSON 配列から同じ分類を行います。後者は CI の説明や外部で生成された文章の明示的なエクスポートにも使用できます。

両方の要求には `provider`、`host`、`repository` と `output` を指定し、直接取得では `credential` も指定します。出力先は公開リポジトリの外の新規ファイルに限定し、結果を標準出力へ流しません。報告には対象の識別子、内容のハッシュ、分類、未取得範囲を保存し、原文や修正命令は含めません。エクスポートの完全性や未取得の CI 説明を検査済みとは扱いません。

独立確認の資料は `-audit-review-basis REQUEST.json` で準備します。`recordsFile` で非公開のエクスポートを指定するか、直接取得用の `credential` を指定します。資料には正確な対象の `record`、設定の `profileHash`、対象と設定を結び付けた `contentHash` を含めます。これは分類結果とは別の、原文を含む非公開の確認資料であり、同じく公開リポジトリ外の新規ファイルへ限定します。確認した各 `record` に独立レビューの結果を `review` として付けて非公開の配列へ保存し、そのファイルを `-audit-file` に渡します。資料から原文や設定を変更した場合、以前の承認では `COMPLIANT` になりません。結果は取得した時点の文章に対するもので、後の変更や未取得の範囲の適合性を主張しません。

分類は `COMPLIANT`、`AUDIENCE_MISMATCH`、`LANGUAGE_MISMATCH`、`INTERNAL_ARCHITECTURE_LEAK`、`ORCHESTRATION_LEAK`、`TEMPORAL_INTEGRITY_FAILURE`、`CONFIDENTIALITY_RISK`、`REQUIRES_PROJECT_DECISION` です。機械的な不適合が見つからないだけでは `COMPLIANT` にしません。正確な文章と設定に結び付いた独立確認が必要です。検査結果を公開プロジェクトへ複製せず、既存記録の修正は対象プロジェクトで別途承認します。

## 未送信の公開予定を取り消す

`taxion records cancel --file REQUEST.json` は、承認済みで送信を開始していない公開予定だけを失効させます。要求は `id`、`previousState: "PENDING"`、`approvalSource`、`contentHash`、`reason`、`actor`、`authorization` を含めます。`contentHash` は `records show` に保存された承認済み予定の `hash` です。時刻は指定せず、成功した取消時に記録します。

同じ内容と承認による再実行は結果を変えません。異なる内容、承認、取消理由または取消権限の再利用は拒否します。取消履歴は追記専用で、元の文章と承認も保持します。取り消した識別子は再承認・送信できません。新しい文章は別の識別子で承認します。

送信済みの公開記録は変更しません。送信中または結果が不明な予定は先に正規の照合手順で解決します。取消は送信を行わず、拒否された操作は保存状態を変更しません。旧版へ戻すと新しい取消状態を解釈できない場合があるため、保存形式を直接編集して回避しません。
