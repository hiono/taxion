# ADR-0045: 公開記録を利用者と貢献者向けの説明に統一する

## Status

採用。公開済みの記録を含むすべての公開面へ即時適用する。監査や個々の是正の完了を意味しない。

## Context

公開コメントに内部の作業手順や通信内容を記載すると、利用者は何が変わり、なぜ必要で、どこまで確認できたのかを読み取れない。将来の貢献者や保守者にとっても、内部の役割名や実行識別子だけでは変更の判断根拠にならない。

## Decision

Issue、PR、レビューコメント、Release Notes、ADR の第一読者を OSS の利用者と将来の貢献者・保守者とする。公開文は変更内容、理由、検証結果を中心に書き、検証した範囲と未確認の範囲を区別する。内部の作業指示や通信ログは非公開の監査証跡で保持し、公開コメントへ転記しない。

標準構成、内部監査との分離、生成文章の検査、訂正手順は [Public Communication Policy](../public-communication-policy.md) に定める。Issue #143 と merge 済みの PR #144 も対象とし、採用した配布設計、協調的な出自検証の保証範囲、実際の検証結果を利用者向けに説明する。merge、review decision、CI result は変更しない。

旧コミュニケーションスタイルからこの方針へ移行する。過去の Issue、PR、Release Notes、ADR を番号や状態で除外しない。編集可能な記録は技術的事実を維持して修正し、編集が不適切または不能な記録は対象を明示した訂正を行う。同じ定型コメントの大量投稿は行わない。

公開文を編集する場合は、変更前の原文と修正内容を非公開で保管する。原文の保護と利用者向け説明の改善を両立させ、判断・検証の事実やコード上の正式な名前を書き換えない。

## Alternatives considered

今後の投稿だけを改善する方式は、利用者が参照する既存の記録に問題を残すため採用しない。単語の一括置換は正当な API・schema の説明も変えるため採用しない。内部証拠の全文公開は変更理由の説明を代替せず、機密情報を露出させるため採用しない。

## Consequences

公開前に読者、技術的意味、検証範囲を確認する必要がある。内部監査は保持できるが、公開要約を別に作成する。自動検査は既知の漏出を検出する補助であり、文脈の確認を代替しない。

## Security and operational impact

機密情報は公開範囲を最小化し、必要に応じて正式な除去手続きを使う。原文の保全記録自体は公開しない。権限不足の対象は未検証として独立して記録し、取得不能を不存在や準拠の証拠にしない。他の対象の是正は継続する。

## Compatibility

文体修正は CLI、公開 schema、Task、Flow、Dispatch の意味を変更しない。commit・tag・Release artifact を書き換えず、失敗や過去の review outcome も保持する。公開処理の検査を変更する場合も、承認した本文と送信本文の一致を維持する。
