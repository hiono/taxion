# ADR-0081: 再設計では旧設計の制約を温存せず、製品を作り直す

Date: 2026-11-14

## Status

Accepted

## Context

Taxion の再設計では、Job を中心とする新しい協調モデルを実現しようとしながら、旧 Task / Dispatch / ReviewFlow の責務、認可方式、API、データ構造、テストを残し、その制約の中で新モデルを成立させようとする傾向があった。

旧モデルと新モデルの責務が矛盾し、旧モデルへの依存が新モデルの自由度を失わせる場合、互換性のための変換・例外・並行経路は設計を複雑化させる。これは設計の進化ではなく、袋小路の延命である。

移行を既存実装の付け替えや新旧両モデルの併存と同一視してはならない。作り直すことで、責務、単純さ、正しさ、利用者価値を改善することが製品開発の目的である。

## Decision

**移行とは付け替えだけではない。作り直すことで製品は良くなっていく。**

この原則を Taxion 全体の再設計・開発に適用する。Authorization だけの局所方針ではなく、Domain Model、Runtime、Role collaboration、API、永続化、CLI、テスト、運用、ドキュメントを含む全領域の判断基準とする。

### 1. 旧設計を残すことを既定にしない

次の条件に該当する旧要素は、長年稼働していたことや既存テストが存在することだけを理由に維持しない。

- 旧モデルの責務や不変条件が新モデルと矛盾する。
- 旧要素に依存すると、新モデルの自由度・単純さ・安全性・拡張性が失われる。
- 互換性のための変換、fallback、例外、二重管理、並行runtimeが複雑さを増やす。
- 新モデルの目的を実現するうえで、その旧要素が不要である。
- 旧要素を残す合理的な製品上・技術上の理由を説明できない。

この場合は旧モデルの責務を新しいドメインに合わせて再設計し、不要な旧コード・API・データ構造・テスト・設定・protocol・コメントを削除する。旧モデルを新モデルの中へ名前だけ変えて移植してはならない。

### 2. 再利用するのは適合する技術的実装に限る

既存コードは調査・学習・比較の資料として扱う。再利用する場合は、新しい責務と不変条件に適合する技術的実装であることを確認する。

ファイル境界の強制、symlink防止、transaction、provenance検証、競合検出などの有効な実装部品は再利用候補となる。一方、旧domain model、旧権限モデル、旧workflow、旧APIの責務や意味を、新設計へ無条件に引き継がない。

### 3. 新しい不変条件から設計とテストを構築する

設計の順序は次のとおりとする。

1. 製品目的、利用者価値、ドメイン概念、責務、状態遷移、不変条件を定義する。
2. 不変条件を強制する境界と実行モデルを設計する。
3. 既存実装を調査し、再利用可能な技術的部品と削除すべき旧依存を分離する。
4. 新モデルを正本とするAPI・保存形式・Runtimeを実装する。
5. 新しい不変条件と利用者シナリオからテストを再構築する。旧挙動を維持するためだけのテストは新しい受入条件へ置き換える。
6. 実際の複数Role協調を含む製品シナリオで、目的の成果が得られることを検証する。

既存テストを通すことを新設計の正しさの代用にしない。テストが旧モデルの制約を固定している場合は、テストも設計とともに作り直す。

### 4. 互換性は目的ではなく、必要性を評価する選択肢とする

互換性は利用者価値、運用上の必要性、データ保全、セキュリティなど具体的な理由がある場合に限って採用する。過去の実装を残すこと自体を目的にしない。

旧データを保持する必要がある場合、履歴読取り・明示的変換・実行可能な現行データを区別する。旧データや旧承認を新モデルの権限・実行条件へ暗黙に変換しない。情報損失や移行不能がある場合は、それを明示して扱う。

### 5. 段階的な置換は認めるが、旧設計の恒久化は認めない

安全に作り直すための段階的実装、短期的な移行境界、明示的な履歴読取りは認める。ただし、それらを理由に旧モデルの並行runtimeや互換fallbackを恒久化してはならない。

一時的に残す旧要素には、具体的な依存、置換先、削除条件を示す。コメントや計画への記載だけで置換完了とみなさず、caller、domain model、API、保存、認可、adapter、テストを実際に変更・削除する。

## Consequences

- 新モデルに不要な旧コード・テスト・API・データ構造を削除する判断が正当な設計成果となる。
- 変更量の少なさや後方互換性の高さを、設計品質の代理指標にしない。
- 既存実装の再利用率より、新しい不変条件の明確さ、強制可能性、製品シナリオの成立を重視する。
- 旧仕様の維持が新しい利用者価値を阻害する場合は、明示的な移行・変更を選択する。
- Taxionの完成判定は、旧コードや既存テストが残っているかではなく、人と複数Roleが目的に沿って協調し、検証可能な成果を得られるかで行う。

## Relationship to existing decisions

- [ADR-0077](0077-job-centered-role-collaboration.md) はJob中心の協調モデルを定義する。本ADRは、そのモデルを旧Task / ReviewFlowの制約に押し込めず実現するための全体原則を定義する。
- [ADR-0080](0080-job-boundary-and-prohibited-effects.md) はJob-native認可の具体的な境界を定義する。本ADRは認可に限らずTaxion全体へ適用する。
- 他のADRや現行仕様と本ADRが矛盾する場合、矛盾する旧設計上の前提を特定し、製品目的と新しい不変条件に基づいて再評価する。古い記述を暗黙に残してはならない。

## Acceptance

- すべての再設計で、旧要素を残す理由と新モデルへの適合性を説明できる。
- 旧要素の削除が新モデルの自由度・単純さ・正しさを改善する場合、削除を選択できる。
- 新しい不変条件を基準にAPI・保存・Runtime・テストを設計できる。
- 互換性のためだけのfallback、二重モデル、変換層を増やさない。
- 実際の利用者シナリオと複数Role協調によって製品価値を検証する。

## Status

Accepted. This ADR is a project-wide design principle and applies to all Taxion redesign and development work.
