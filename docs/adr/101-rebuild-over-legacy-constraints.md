# ADR-101: 旧設計の制約を温存せず、製品目的から再構築する

Date: 2026-11-20

## Status

Accepted

## Context

既存モデルの責務、不変条件、認可方式、API、データ構造、テストを残したまま、新しいJob中心の協調モデルをその制約内で成立させようとすると、新モデルの自由度、単純さ、安全性、拡張性が失われます。互換性のための変換、例外、fallback、二重管理、並行runtimeは複雑さを増やし、製品目的の実現を妨げます。

## Decision

**移行とは付け替えだけではありません。作り直すことで製品を良くします。**

この原則をDomain Model、Runtime、Role collaboration、API、永続化、CLI、テスト、運用、ドキュメントを含むTaxion全体へ適用します。

### 1. 旧設計を残すことを既定にしない

次の条件に該当する既存要素は、稼働実績や既存テストの存在だけを理由に維持しません。

- 旧モデルの責務や不変条件が新モデルと矛盾する。
- 旧要素への依存が、新モデルの自由度・単純さ・安全性・拡張性を失わせる。
- 互換性のための変換、fallback、例外、二重管理、並行runtimeが複雑さを増やす。
- 新モデルの目的を実現するうえで、その旧要素が不要である。
- 旧要素を残す合理的な製品上・技術上の理由を説明できない。

該当する場合は旧モデルの責務を新しいドメインに合わせて再設計し、不要な既存コード・API・データ構造・テスト・設定・protocol・コメントを新しい実装から排除します。旧モデルを新モデルの中へ名前だけ変えて移植しません。

### 2. 再利用するのは適合する技術的実装に限る

既存コードは調査・学習・比較の資料として扱います。再利用する場合は、新しい責務と不変条件に適合する技術的実装であることを確認します。

ファイル境界の強制、symlink防止、transaction、provenance検証、競合検出などは再利用候補です。一方、旧domain model、旧権限モデル、旧workflow、旧APIの責務や意味を、新設計へ無条件に引き継ぎません。

### 3. 新しい不変条件から設計とテストを構築する

設計と実装の順序を次のとおりとします。

1. 製品目的、利用者価値、ドメイン概念、責務、状態遷移、不変条件を定義します。
2. 不変条件を強制する境界と実行モデルを設計します。
3. 既存実装を調査し、再利用可能な技術的部品と削除すべき旧依存を分離します。
4. 新モデルを正本とするAPI・保存形式・Runtimeを実装します。
5. 新しい不変条件と利用者シナリオからテストを構築します。旧挙動を維持するためだけのテストは新しい受入条件へ置き換えます。
6. 実際の複数Role協調を含む製品シナリオで、目的の成果が得られることを検証します。

既存テストを通すことを新設計の正しさの代用にしません。テストが旧モデルの制約を固定している場合は、テストも設計とともに作り直します。

### 4. 互換性は目的ではなく、必要性を評価する選択肢とする

互換性は利用者価値、運用上の必要性、データ保全、セキュリティなど具体的な理由がある場合に限って採用します。過去の実装を残すこと自体を目的にしません。

旧データを保持する必要がある場合、履歴読取り・明示的変換・実行可能な現行データを区別します。旧データや旧承認を新モデルの権限・実行条件へ暗黙に変換しません。情報損失や移行不能がある場合は、それを明示して扱います。

### 5. 段階的な置換は認めるが、旧設計の恒久化は認めない

安全に作り直すための段階的実装、短期的な移行境界、明示的な履歴読取りは認めます。ただし、それらを理由に旧モデルの並行runtimeや互換fallbackを恒久化しません。

一時的に残す旧要素には、具体的な依存、置換先、削除条件を示します。コメントや計画への記載だけで置換完了とみなさず、caller、domain model、API、保存、認可、adapter、テストを実際に変更・削除します。

### 6. 既存実装・候補実装の評価

既存実装や候補実装は、技術的な再利用可能性を評価する対象とします。既存実装が存在すること、テストが存在すること、過去に成功したことだけでは採用を決定しません。

採用判断では、対象を次のいずれかに分類します。

- **直接採用:** provenance、利用条件、設計適合性、安全性、保守性および受入れ証拠が確認でき、新Taxionの不変条件を満たす場合。
- **部分採用:** 独立した技術部品または限定した責務だけが適合し、その範囲を切り出して検証できる場合。
- **追加検証・修正後に採用:** 価値は見込めるが、設計適合性・安全性・動作証拠の不足が特定され、修正後の再検証が可能な場合。
- **再実装:** 既存モデルや責務が新しい設計と矛盾する、または修正コスト・安全性・保守性が採用利益を上回る場合。

評価では、出所、作成経緯、利用条件、対象SHA、実行環境、依存関係、設計適合性、安全性、保守性、受入れ証拠を確認します。確認できない項目は未確認として残します。コード・データ・履歴を一括移植しません。採用対象と範囲が確定した場合は、対象領域のADRと実装Issueへ反映します。

## Consequences

- 新モデルに不要な旧コード・テスト・API・データ構造を削除する判断を、正当な設計成果として扱います。
- 変更量の少なさや後方互換性の高さを、設計品質の代理指標にしません。
- 既存実装の再利用率より、新しい不変条件の明確さ、強制可能性、製品シナリオの成立を重視します。
- 既存仕様の維持が新しい利用者価値を阻害する場合は、明示的な変更を選択します。
- Taxionの完成判定は、人と複数Roleが目的に沿って協調し、検証可能な成果を得られるかで行います。

## Acceptance criteria

- 旧要素を残す場合、その理由と新モデルへの適合性を説明できます。
- 旧要素の削除が新モデルの自由度・単純さ・正しさを改善する場合、削除を選択できます。
- 新しい不変条件を基準にAPI・保存・Runtime・テストを設計できます。
- 互換性のためだけのfallback、二重モデル、変換層を増やしません。
- 実際の利用者シナリオと複数Role協調によって製品価値を検証します。

## Alternatives considered

- **旧コードをそのまま移植する:** 旧モデルの責務・不変条件・認可・実行経路まで持ち込む危険があるため採用しません。
- **旧コードをすべて破棄する:** 適合する技術的実装や候補実装から得られる証拠まで失うため採用しません。
- **候補PoCを無条件に製品実装へ昇格する:** 候補実装であることと新Taxionの設計適合性・受入れ証拠は別であるため採用しません。
- **既存テストの通過を新設計の正しさとみなす:** 旧モデルの制約を固定する可能性があるため採用しません。
## Relationship to other ADRs

ADR-100はTaxionが実現する製品価値を定義します。本ADRは、その目的を実現するための全体再構築原則を定義します。本ADRは製品目的を再定義せず、Job、Role、認可、通信、永続化等の具体的な設計契約は下位ADRに委ねます。
