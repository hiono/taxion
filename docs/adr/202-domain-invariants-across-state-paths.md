# ADR-202: ドメイン不変条件を生成・変更・保存・復元の全経路で強制する

Date: 2026-11-20

## Status

Accepted

## Context

ドメインの判定関数が存在することと、その条件がシステム全体で守られることは同じではありません。状態変更が判定関数を迂回できる場合、保存時や復元時だけの検証では、不正な状態や外部副作用との不整合が一度成立する余地があります。

Job、承認、RoleExecution、Provider operation、Worktree ownership、成果、証拠の整合性は、単一の入口だけでなく、永続化、外部入力、復旧、再送、競合を含むすべての状態変更経路で維持する必要があります。

## Decision

**ドメイン不変条件はドメインモデルの規範とし、状態を生成・変更・受入れ・復元するすべての経路で成立することを必須とします。**

### 1. 規範と実装の対応

1. 不変条件は対象状態、前提条件、成立条件、例外条件を明示した論理式または同等の形式で定義します。
2. コードは定義を実行可能な形で表現します。判定関数の存在だけでは実装完了とみなしません。
3. 状態変更は、変更後の状態が不変条件を満たす場合に限り成立させます。
4. 保存データの読込み、移行、復元、外部入力も信頼境界として検証します。
5. 不変条件を満たさない場合はfail-closedとし、部分的な状態変更を残しません。

### 2. 強制対象となる経路

各不変条件の性質に応じて、少なくとも次の経路を評価します。

- 新規生成・初期化
- 状態遷移および関連データの更新
- JobAggregate / graphの検証
- 永続化直前と永続化後の再読込み
- JSON等の外部表現からの復元
- migration、backup、restore、recovery
- Controller / Runtimeによる外部実行直前の権限・予算・期限・scope再検証
- 競合、再送、重複実行、実行状態不明からの復旧

すべての不変条件に同じ検証箇所を機械的に追加しません。各条件について、どの経路が状態を変更し、どの境界で強制するかを設計上明示します。

### 3. 判定・強制・検証を区別する

次の3つを別々の完了条件として扱います。

- **判定:** 不変条件を評価する規範的な判定ロジックが存在すること。
- **強制:** 不変条件に違反する状態変更・保存・実行を成立させないこと。
- **検証:** 正常系と違反系を含め、対象となる全経路で強制されることをテストとコードレビューで確認できること。

違反を検出するvalidatorと、違反状態の生成を防ぐmutation gateは役割が異なります。必要に応じて両方を設けます。復元時の検証は、過去に保存された不正状態を現在のモデルへ持ち込ませないために必要です。

### 4. テストと証拠

- 正常条件を満たす状態変更が成功することを確認します。
- 不変条件に違反する状態変更が拒否されることを確認します。
- 拒否後に元の状態、履歴、永続データが変更されていないことを確認します。
- 不正な保存データ、外部入力、移行データの復元が拒否されることを確認します。
- 同じ不変条件を複数の経路から検証し、経路ごとのテスト対象を追跡可能にします。
- テストが通った事実だけで全経路の網羅を主張しません。実装上の入口と呼出し関係を調査し、未確認経路を明示します。

### 5. 適用範囲

本決定はJob、Task、RoleExecution、JobApproval、PlanningAuthorization、JobMessage、Provider operation / observation、Worktree ownership、JobOutput、JobEvidence、JobUsageおよび今後追加するドメインモデルに適用します。

認証・認可、承認、秘密情報、データ整合性、二重実行防止、不可逆操作、予算、期限、成果物provenance、Provider停止・結果照合は必須不変条件として扱います。

## Alternatives considered

- **判定関数の存在だけで不変条件を満たしたとする:** mutation経路が判定を迂回できるため採用しません。
- **保存時だけ検証する:** 不正状態が生成されてから保存までの間に成立するため採用しません。
- **復元・migration・外部入力を信頼済みとして扱う:** 過去または外部の不正状態を現行Jobへ取り込むため採用しません。
- **すべての不変条件を一つの検証箇所へ機械的に集約する:** 条件ごとに異なる変更経路と強制境界を無視するため採用しません。
## Consequences

- ADRの論理条件、ドメイン判定、状態変更gate、aggregate validation、テストを追跡可能にします。
- 判定関数があっても未適用経路があれば未完了として扱います。
- 状態変更の入口と復元境界を棚卸しします。
- 不変条件の変更時には、影響する全経路と既存データへの影響を再評価します。
- テスト成功は重要な証拠ですが、未調査の経路を含む全体保証とは区別します。

## Security and operational impact

安全に関する不変条件を利便性、性能、変更量で相殺しません。権限、承認、秘密情報、scope、予算、期限、二重実行、不可逆操作、実行状態不明は、対象操作の直前にも現在の状態に基づいて検証します。検証不能な場合は実行を許可しません。

## Acceptance criteria

- 各不変条件について対象状態、前提、成立条件、例外条件と強制境界を追跡できます。
- 生成・変更・保存・復元・migration・外部入力・再送・recoveryの該当経路で不変条件を強制します。
- 違反操作の拒否後に状態・履歴・永続データが変更されません。
- validatorの存在だけで強制完了とせず、実際の入口と呼出し経路の検証証拠を保持します。
- 未調査経路を網羅済みと報告しません。
## Relationship to other ADRs

- ADR-100は製品目的を定義します。
- ADR-101は旧設計の制約を温存しない再構築原則を定義します。
- ADR-201はJobAggregateとCommand境界を定義します。
- ADR-500はJob authority、禁止副作用、Observation / Admission / Execution Permissionを定義します。
- ADR-202は上記の不変条件を全状態変更経路で強制する横断的な規範です。各下位ADRは固有の不変条件と強制経路を具体化します。
