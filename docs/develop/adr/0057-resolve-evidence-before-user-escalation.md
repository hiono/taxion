# 57. 利用者への差戻しを新しい意思決定に限定する

Date: 2026-10-28

## Status

Accepted。Issue #210。ADR-0055 の全工程方針を、差戻し経路の判断と結果受理に具体化する。
配布済み CLI や実行中の旧指示を変更する判断ではない。

## Context

既存証拠から解決できる申告の違いを契約違反として扱うと、実装の再実行と人間の再確認を
繰り返し、検証・独立レビューに到達するための予算を消費する。個々のエラーを無条件に
無視する修正では、同じ問題を他の入口へ移すか、権限・品質の検査まで失う。
判断の責任と、その判断を裏付ける決定的な検査を分離する必要がある。

## Decision

外側 Controller は全ての差戻し候補について、未解決の人間の判断を特定する。
既存承認と安全に取得できる証拠で解消できる場合は、自ら対処して承認済みの次工程へ進める。
新しい目的・受入条件・範囲・権限・予算・期限・公開許可、または承認済み観測では
得られない必須情報がある場合だけ、差分と影響をまとめて利用者へ尋ねる。
技術的失敗や不明な実行状態は、それ自体を新しい承認の要求には変換しない。
安全に解消できなければ成果と具体的な技術的阻害を保持して停止し、成功も承認も創作しない。

共通の担当指示を ready・Planner・質問・Coder・Reviewer・カスタム担当へ一度ずつ適用する。
管理スキルも同じ判断を使う。製品の担当は管理操作へ転向せず、外側 Controller が
契約と証拠を統合する。追加の評価モデルや汎用的な自動復旧エンジンは作らない。

### 差戻し経路の棚卸し

| 経路と主な実装 | Controller の判断・処理 | 維持する境界 |
|---|---|---|
| 計画・質問：`plan.go`、`request_plan.go`、`question.go` | 保存された回答・観測・可逆な選択で解消し、既存の未回答事項だけをまとめる | 意思決定が未記録なら承認を創作しない |
| 契約・設定：`intake.go`、`configuration.go`、`gate_report.go` | 正式確認から導出済みの承認束を再利用し、単なる記録形式差を再承認にしない | scope、設定、仕様利用許可の実変更は正式承認 |
| 提出：`controller.go`、`gitproof` | 新規 Coder の変更一覧を実 Git 差分から確定し、直接受理と自動実行で共用する | repository、candidate、全実変更の範囲検査 |
| 検証・レビュー：`reviewflow.go`、`result_schema.go` | 同じ確定成果物の実検証後に独立 Reviewer へ渡す。申告の再転記を求めない | 検証失敗・未検証・Reviewer の変更・未裏付けの承認を拒否 |
| 修正・保留：`repair_status.go`、`draft_approval.go` | 承認枠内の修正は内部遷移とし、状態照会から無条件に人間へ返さない | HOLD と未承認 draft を進行許可にしない |
| 停止・復旧：`recovery.go`、`cancellation.go`、`intake.go` | 既存停止証跡と成果を再利用し、必要な正式な後続契約を準備する | 不明な配送、旧実行との競合、終端履歴、予算の再利用禁止 |
| 課金・時間：`stage_budget.go`、`budget_guidance.go` | 既存観測と承認方式で判断する。提出待ちも工程内として扱う | 未知の残量を創作せず、上限・期限を延長しない |
| 公開：`publication.go`、`publictext` | 既存の正確な内容承認と配送証拠を再利用する | 内容変更、別公開先、配送不明の再送は許可しない |

### 変更一覧の共通受理

新規 Coder instruction は `changeManifestPolicy: git-diff-v1` を保持する。
Controller は baseline から output commit/tree までの全差分を正規の `changedFiles` とし、
生の申告一覧を `changeManifest.reportedChangedFiles` に保持する。
`changeManifest` は policy、baseline、output commit/tree と結び付いた Controller 証拠であり、
モデルや結果ファイルからの指定を拒否する。元の実行イベント・提出ファイルは書き換えない。
既に保存済みの結果や result hash も変更しない。

省略・重複・今回編集分だけ・過剰な申告は、それだけでは失敗にしない。
申告にだけ存在するパスはアクセスに使わず、実差分の全パスを検査する。
検証前後の同一 candidate、commit の clean 条件、snapshot の固定 tree を照合する。
後段の照合・修正・復旧・Reviewer 引継ぎも正規の一覧を使う。
Reviewer 自身の `changedFiles` は空であり、この補完の対象にはしない。
Coder の失敗・中断や品質判定を、一覧の補完で成功へ変更しない。

## Compatibility and rollback

policy のない保存済み指示は完全一致条件を維持する。未知の policy は拒否する。
旧 session・契約・承認 hash は再生成せず、新方式は新規発行から適用する。
新しい DB schema は追加しない。旧 binary は新しい instruction/result field を解釈できると
仮定しない。更新前に workspace を保全し、新方式の保存後は旧版で同じ workspace を操作せず、
戻す場合は更新前の整合した保全一式を別環境で使う。更新後の成果・監査証拠は削除しない。

## Validation and remaining work

モデルを起動しない回帰試験で、commit・snapshot の持込み差分、申告の省略・重複・過剰、
元申告の保持、検証後の再照合、旧 policy の維持、範囲外変更・偽造証拠・candidate 不一致の
拒否を確認する。自動 Flow と段階実行は、省略申告から検証・独立レビュー・許可済み修正・
再レビューまでの接続を確認する。全役割の共通指示にも差戻しの判断基準を要求する。

この変更は任意の拒否の自動解除ではない。scope 追加後の停止・正式契約更新・
後続開始を一操作へまとめる機能、低速出力の原因測定、自動的な残量保証は実装しない。
これらは既存の公開操作と承認枠で扱い、未対応の組合せを Controller が実装済みと説明しない。
仕様の全工程適用と、各自動復旧機能の実装完了を区別する。
