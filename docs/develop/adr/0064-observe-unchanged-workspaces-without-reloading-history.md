# 64. 変更のない台帳の監視で履歴全体を再取得しない

Date: 2026-11-02

## Status

Accepted

## Context

期限監視は 250 ms ごとに `LoadWorkspace` を呼び、回答受信中の工程確認も毎秒、
同じ保存状態を読み直していた。状態取得は共有文字列と全記録の展開、JSON 解析、
Graph と監査の検証を含む。小さい回答断片そのものにはこの取得処理はないが、
同じ受信ループ内の定期確認と、Store の mutex を共有する期限監視が履歴量の影響を受ける。

履歴を削除したり、監査記録を間引いたりする方法は採らない。
合成履歴の比較結果は[イベント観測の検証](../event-observation-validation.md)に記録する。

## Decision

`Store.ObserveWorkspace` は、同じ読み取り取引で得た変更番号と検証済み状態を対応させる。
変更番号が同じ間は状態の再展開を省き、変われば通常の完全検証を行う。
callback は状態を変更・保持しない。通常の `LoadWorkspace` と更新取引はこの再利用を使わない。

稼働中の確認と正式遷移は `runningFlowStop` の停止条件を共有する。
観測で遷移不要と確認できる間は保存処理を呼ばず、停止や引継ぎが必要なら、
従来の正式遷移が取引内で条件を再確認する。時刻と外部 Memory は変更番号に依存せず毎回確認する。
operation-lock、所有権、結果受理、重複照合、利用量保存は変更しない。

## Consequences

変更のない監視では、履歴の展開量は監視回数に比例しない。
最初の観測と変更後の取得・正式保存には、履歴量に応じた処理が必要になる。
保存形式や CLI の入力契約は変えず、管理スキルは 1.3.19 を維持する。
直接 SQL での現場修復や保存結果の書換えは、この設計の運用手順には含めない。
