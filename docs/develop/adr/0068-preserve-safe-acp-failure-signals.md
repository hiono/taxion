# 68. ACP の停止と提供元の報告を区別して保持する

Date: 2026-11-03

## Status

Accepted

## Context

Issue #231 では、直接実行で確認した無料利用制限と、ACP の応答前停止の因果が
未確定である。工程の context が送信直後に解除される不具合は `809b88e` で修正したが、
それによって全停止を説明できるわけではない。従来の adapter は標準エラーを捨て、
RPC エラーの本文もすべて伏せるため、取得できた制限報告も診断に届かなかった。

## Decision

標準エラーの末尾4096バイトだけをメモリ内に保持する。RPC エラーの `message` と `data`、
標準エラーから、既知の固定句 `Free usage limit reached` を大文字小文字を区別せず照合する。
保存・表示するのは固定値 `free-usage-limit-reported` または `unknown` と取得経路だけで、
原文・認証情報・内部パスは診断へ転記しない。部分一致は提供元の報告の観測であり、
課金契約の検証や過去の停止原因の確定ではない。

RPC の拒否は code と `RPC provider signal`、応答なしの切断は
`stderr provider signal` をエラーへ含め、既存 Controller の `failed` 記録へ接続する。
応答受理と process 終了が同時なら、既に届いた RPC 応答を先に読む。
標準エラーに報告があるだけで正常応答を失敗へ変えず、取消と期限切れも既存の
context による理由を維持する。認証・通信・枠不足を未知の文面から推測しない。

adapter の設定識別子を `openacp-isolated-v14` にする。旧契約・session・結果・停止記録を
遡及変更せず、自動再送、モデル変更、有料経路への切替、利用枠の引上げを追加しない。
未取得の利用量は引き続き `acp_usage_unavailable` であり、ゼロ・無料・無制限ではない。

## Consequences

この変更はオフラインの診断・回帰確認である。追加モデル実行は承認されておらず、
現在の実 OpenCode による成果保存・Controller 検証・同一対象の独立レビューは未実施のまま、
Issue #231 を開いて保持する。過去の実証を消さず、現在の受入れの代わりにも使わない。
確認表と再開手順は [バックエンド別の確認記録](../backend-acceptance.md)に保存する。

末尾から失われた文面、未知の文面、標準エラーへも出ない内部ログは分類できない。
原文の保存やログ探索を自動追加しない。必要な調査・実証は構成、費用、期限、
保存範囲の差分承認を得てから行う。実サービスの成功やトークン削減率は主張しない。
