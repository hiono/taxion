# ADR-0066: 観測記録・受入れ判定・実行許可を分離する

## Context

停止時の部分成果は、旧契約の許可パス検査に失敗すると記録できない。
一方、後続契約の確定はその記録を必要とする。この組合せでは、契約外の変更が
あるという事実を評価したくても、証拠不足のため次の仕事を開始できない。
実行セッションがある取消を未開始扱いすることや、元結果の成功への変更は解決にならない。

Issue #248 は役割の成果を固定した工程順ではなく、対象・目的・証拠・権限で
受け入れる構造を求める。計画、実装、レビュー、人の成果の出所は残すが、
作成者の成功を観測や診断に共通する前提にはしない。

## Decision

観測は「今どの対象があるか」、適合判定は「どの契約を満たすか」、
受入れは「次の仕事の入力にできるか」、実行許可は「何を実行できるか」として分ける。
共通の観測記録と副作用のない型付き判定を既存の Go Controller 内に置く。
CLI の確認と正式確定は同じ判定を使い、古い結果や期限を変更しない。

観測には対象の完全な識別、出所、取得時点、明示した読取り範囲、元の仕事への参照を付ける。
旧契約への不適合は観測の失敗に置き換えず、別の判定結果に残す。
新たな観測範囲の承認は旧契約に遡及しない。秘密・禁止パスや読取り権限は維持する。
停止後の観測は停止時の取得証拠ではなく、変更の作者や時刻を推定しない。

受入れ判定は、対象照合、出所、証拠の不足、稼働所有権、実行不明、
適用するルール、阻害理由、次に必要な操作を構造化して返す。
既存記録で補える事項を先に調べ、人間の判断が必要な差分を区別する。
判定の `accept` は契約確認の入力にできるという意味であり、実行・品質・公開の許可ではない。
契約確定と実行開始では、対象・承認・予算・期限をそれぞれ再確認する。

Jev の着想から採用するのは、小さい判断を型付きで返し、処理の分岐をコードで行う構造である。
識別や権限の判定に有料モデルは使わない。意味評価が必要な仕事は既存の独立レビューへ渡す。
新しい提供元、モデル、資格情報、フレームワークは追加しない。

### 原典と主張の境界

具体的な取得は `workflow observe-input`、保存済み提案の確認は
`workflow assess-input` とする。`InputDecision` は可否、参照状態、
阻害理由、証拠の出所、解消方法、承認差分、次の操作を返す。
既存のパス検査と新しい受入れ判定でこの型を使い、分岐はコードで行う。
旧処理結果とは別に追記した観測を、`observationHash` で提案と確定の両方に束縛する。
元結果の具体的な阻害理由・検証出力・未知事項も担当への指示に含め、
参照ハッシュだけを診断として渡さない。

2026-11-02 に次の一次資料を確認した。

- [TypeSafe Introduction](https://docs.typesafe.ai/introduction) は Jev を
  状態と型付き質問から判断を返すモデルと説明し、原子的な質問をコードで合成することを推奨する。
- [TypeSafe Confidence](https://docs.typesafe.ai/confidence.md) は
  `Choice` / `Score` の確信度を確率分布から導出する統計量と説明する。
  汎用モデルが自己申告した数値を、この較正済み確率と同一視しない。
- [OPA Documentation](https://www.openpolicyagent.org/docs) は判定と強制を分離し、
  入力に対する構造化した判定結果を呼出し元で利用する方式を説明する。
  この責務分離を採用し、OPA 自体は導入しない。
- [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
  は対応するスキーマの出力制約と、拒否・中断などの扱いを説明する。
  構造の制約は意味の正しさ、内部推論の禁止、確率の較正を保証しない。

プロンプトの「思考禁止」、`temperature: 0`、小さい出力上限だけで
決定性・判断精度・速度・費用を保証する案は採用しない。
小さい上限による中断を有効な判定にせず、提供元の広告値を Taxion の性能として扱わない。
Jev 互換 API の実装や実測性能の比較は、この設計判断から導かれる必須条件ではない。

## Alternatives considered

取消の特定状態だけを許可する例外は、観測と認可の結合を残すため採用しない。
旧部分成果の検査を一律に外す案も、記録を承認済みの成果と取り違えるため採用しない。

各入口に別々の判定を置く案は、確認と実行で異なる結果を返す危険がある。
判定は共通化し、Git の観測と各操作の副作用は境界に残す。
独立サービスや汎用工程エンジンは運用と移行の費用が増え、現在の問題に不要である。

## Consequences

既存の証拠を使える場合は再観測や前工程を要求しない。
新しい観測が必要な場合も、保存済み結果とは区別した追記記録を使う。
受入れを確認する操作と実際の契約確定を接続し、助言だけの行き止まりにしない。

一般化した観測・判定の実装は、全入力形式への対応を意味しない。
未対応形式、取得できない証拠、実行不明は明示した阻害条件として残す。
外部利用環境で元の作業が検証と独立レビューへ到達し、受入れ条件を満たすまでは
Issue #248 の必須ゲートを完了としない。

## Security and operational impact

観測自体にモデル・検証コマンド・修正の権限を与えない。
新しい観測範囲と正確な対象を明示して確認し、禁止パスを勝手に広げない。
別の稼働処理がある間は記録や継続を確定しない。
不明な実行を再送せず、正式な停止記録、累計消費、元の結果と承認を保持する。
期限・予算の不足は停止条件であり、観測や判定を理由に上限を増やさない。

## Compatibility

既存記録の意味は変えない。新たな記録を使う前にデータベース・Git・設定を保全する。
新形式を含む保存先を旧版で更新しない。戻す場合は新形式保存前の保全状態を別配置で使う。
新たな観測は旧実行の部分成果を補記したものではなく、独立した取得記録として扱う。
