# 24. 利用者の受け渡し制御と本流を変更しない質問

Date: 2026-10-11

## Status

Accepted

[ADR-0021](0021-durable-task-graph-and-dispatch-change-control.md) の変更管理を、
利用者が ROLE の出力を読みながら相談・補足する対話へ接続する。
以下は採択した設計であり、現在の実装状況は Issue と参照仕様に記録する。

## Context

手動で ROLE 間をコピーする運用では、利用者が結果を読んで補足してから
次の担当へ渡せる。自動進行では、読んでいる結果と現在の実行段階がずれ、
補足が意図しない担当や古い指示へ適用される可能性がある。

利用者は修正指示を書く前に、現在の状態、判断の根拠、調査不足を確認したい。
質問だけで方針が変わると気軽に確認できず、質問中の発見が本流に残らなければ
同じ見落としを繰り返す。指示の送信制御と、変更を伴わない質問を分けて扱う。

## Decision

### 次の受け渡しの保留と現在の実行中断を分ける

「次を待つ」は後続指示の発行・開始を保留し、現在の許可済み実行を維持する。
「いま止める」は後続を保留したうえで現在の実行へ中断を要求する。
Task の取消、Dispatch の取消、一時的な受け渡し保留は別の事実として保存する。
中断要求の受付と停止確認を区別し、停止の証拠なしに競合する実行を始めない。
途中成果、commit、外部更新を自動で巻き戻さない。

保留受付と指示の発行・開始を共通 controller の永続 transaction で順序付ける。
自然言語の解析や回答が完了する前に、明示的な保留要求を保存する。
既に発行・開始された場合はその状態を返し、未送信として扱わない。
発行済み・未開始の Dispatch も保留中に実行を開始できないようにする。

### 指示案の改訂と Dispatch の発行を分ける

Orchestrator は解釈、次の担当、操作、対象 SHA、未確認事項を含む指示案を示す。
指示案は版と根拠を持ち、未発行なら補足を受けて改訂できる。
発行時に観測対象、指示案の版、保留状態、Task 契約と承認を再照合する。
古い版や不一致を明示的に拒否する。

発行済みの instruction と履歴は変更しない。発行後の変更には ADR-0021 の
AMENDS、SUPERSEDES、SUSPENDS、RESUMES などの関係と停止証拠を使う。
scope、acceptance、実行主体、契約、費用・上限の変更は必要な承認を得る。
通常の説明追加や質問を承認として扱わない。
Reviewer の指摘への利用者の異議は元の verdict と対象 SHA を維持して記録し、
再確認または明示的な承認済み例外へ接続する。

### 状況・根拠の質問は本流を変更しない

脇の質問は作業、承認、指示案、ROLE session の本流の会話履歴を変更しない。
既存の状態・判断・証拠を読み、現在の担当、作業、後続予定、確認済み、
仮定、未確認を区別して返す。根拠が記録にない場合は「確認できない」と返し、
内部思考を推測した説明や後付けの正当化をしない。

回答には対象 Task、Dispatch、出力の版・SHA、観測時点と出典を付ける。
永続記録の観測と実 runtime・Git・認証のライブ照会を区別する。
回答中も本流が進むことを明示し、必要なら「保留してから質問」を選べる。
質問そのものから実行保留を推測しない。

脇で追加調査する場合は読み取り専用とし、必要な権限・費用・上限を照合する。
今回調べたことと、それ以前から確認済みだったことを区別する。
通常の質疑の全文を本流へ入れず、利用者が明示的に反映を求めた場合に限り、
発見事項、証拠、対象、変更理由、利用者の指示の出典を正式な記録へ転記する。
既存の安全停止条件の違反を検出した場合は、質問経路でもその条件に従う。

### フィードバックは利用者が観測した対象へ結び付ける

計画への補足は計画案の版、コードへの補足は成果物 SHA、
レビューへの返答は指摘と対象 SHA に結び付ける。
全体方針への発言は別の対象として扱い、常に最新 ROLE へ割り当てない。
UI は対象を表示し、利用者に内部 ID の手入力を強制しない。
曖昧さによって操作が変わる場合は確認する。

反映時は現在の状態を再取得し、観測からの変化を照合する。
対象が古い場合は拒否または明示的な再確認とし、黙って新しい結果へ付け替えない。
同じ利用者の入力の再送で指示・判断・実行を重複生成しない。

### 見ながら進める操作を基本とし、自動進行を明示的に選ぶ

会話 UI では ROLE の進捗・証拠・不確実性と次の指示案を表示する。
計画から実装、レビュー後の修正方針、許可が必要な公開操作を主な確認点とする。
token や tool 呼出しごとの確認は求めず、返答のない時間を承認扱いにしない。
自動進行は許可済み範囲・上限とともに明示的に選択し、途中介入を維持する。
入力中の自動保留は UI の補助とし、明示的な保留操作の代用にしない。
既存の非対話 workflow はこの採択だけでは既定動作を変更しない。

## Consequences

M12 で共通 controller と CLI の保留・反映・質問を実装し、実 SDK の受入れ条件に含める。
M13 で再起動・複数 process・重複入力・発行との競合から復旧できることを検証する。
M15 の ACP サーバーは CLI と同じ契約・保存状態へ接続する。
Web UI と端末間の利用者別 session 所有権は、必要性が具体化した場合に別途評価する。

既存の `task plan` を永続記録に基づく観測の基礎として再利用する。
観測内容の hash は回答の同一性を示すが、実行権限や現在性の証明にはしない。
保留や反映には別途、現在状態と発行・開始の transaction 内検査が必要である。
既存の `runtime stop` は取消であり、実行中の `Send` は busy を拒否するため、
追加プロンプト送信だけでこの契約を実装したことにはしない。
