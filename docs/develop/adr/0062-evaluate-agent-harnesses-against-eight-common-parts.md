# 62. エージェントハーネスの8要素を判断基準として維持する

Date: 2026-10-30

## Status

Accepted。8要素を設計・実装・受入れの判断基準として採択する。
採択は全要素の実装完了、即時の再実装、モデル実行や追加予算の承認を意味しない。

## Context

Taxion は製品開発を進めるためのツールであり、ハーネス自体の再実装を目的にはしない。
一方、現在の実装にない機能を「上位の承認管理が主な役割だから」と対象外にすると、
隔離、並列委譲、継続、停滞からの回復といった利用者の要求が追跡から失われる。

2026-10-30 に `main @ 082c40f` の実装と ADR を読み取り専用で評価した。
Taxion は承認・役割分離・永続記録・検証を管理し、モデルとツールの反復や履歴圧縮は
Copilot SDK / OpenCode に委ねている。この分担を維持しながら、システム全体として
何を満たし、何が不足しているかを判定する共通基準が必要である。

## Decision

### 8要素と個別の判定項目

以下の各項目を採択済みの要求として保持する。ID は実装と証拠の対応に用い、
既存機能の名前を変えただけで充足したとは判定しない。

| 要素 | 判定項目 |
| --- | --- |
| H1 ループ | H1.1 コンテキストをモデルへ送り、要求されたツールを実行する。H1.2 結果を次のステップへフィードバックする。H1.3 タスクの終了を判断する。 |
| H2 ツールとサンドボックス | H2.1 ターミナル、ファイル、ブラウザ、接続されたアプリを利用できるようにする。H2.2 すべてのタスクを独立したコンピューター内で実行する。H2.3 不適切なコマンドによる被害をサンドボックス内に留める。 |
| H3 サブエージェント | H3.1 メインエージェントからサイドタスクを引き取り、並行して実行する。H3.2 それぞれを新しいコンテキストウィンドウで開始する。H3.3 メインコンテキストを圧迫しない短いサマリーを返す。 |
| H4 コンテキスト管理 | H4.1 モデルが毎ターン見る内容を決める。H4.2 タスクが必要とする場合にのみスキルやファイルをロードする。H4.3 コンテキストウィンドウが満杯になる前に古い履歴を要約する。 |
| H5 メモリ | H5.1 進捗ノート、Git 履歴、スキルをディスクに保存する。H5.2 新しいセッションから前回の作業を読めるようにする。H5.3 停止したところから作業を再開する。 |
| H6 ガードレール | H6.1 メール、支払い、削除などの高リスク操作を承認待ちにする。H6.2 本物の認証情報をサンドボックス外に保つ。H6.3 プロンプトインジェクションに、盗める認証情報を与えない。 |
| H7 検証 | H7.1 成功を装ったサマリーだけで完了させない。H7.2 テスト、ブラウザチェック、または独立した評価を先に実行する。H7.3 必須チェックの合格後にのみタスク完了を許可する。 |
| H8 観測可能性 | H8.1 すべてのモデル呼出しとツール呼出しを追跡する。H8.2 同じ失敗した編集の反復を検知する。H8.3 別のアプローチを試すよう促す。 |

### Taxion と runtime の責任分担

Taxion 内での再実装は必須にしない。SDK、CLI、OS、外部実行環境へ委譲してもよいが、
提供元、対応構成、能力の確認方法、証拠、失敗時の挙動を特定する。
委譲先に API があることだけでは、その機能の有効化や実動作を確認したことにはならない。

H2 の「独立したコンピューター」は、単なる別 session・process・worktree への分離では
満たさない。仮想環境などを採用する場合も、タスク間とホストのファイル・process・
認証情報・外部副作用の境界を明示し、隔離要件を満たす証拠を要求する。
OS や runtime の制限で満たせない構成は未対応として残し、全タスクの隔離を達成したとは表示しない。

H2.1 は全タスクへ全ツールを無条件に付与する要求ではない。
必要な能力を承認済みの範囲で利用できることと、不要な能力を与えないことを両立させる。
ネットワークや接続アプリの副作用はファイル隔離だけでは封じ込められないため、
H6 の権限・認証・操作承認と併せて判定する。

H3 の並列委譲は、逐次 Coder / Reviewer やモデルを使わない並列 lane とは区別する。
独立レビューの文脈・判定の独立性、親子の総予算と期限、二重実行防止を維持する。
H5 の再開も、不明な外部実行を無条件に再送する意味にはしない。

H7 の検証は、対象成果物と必須チェックの証拠に基づく。
model-free Task の利用者申告の完了は、Taxion が実行・独立検証した完了と区別する。
H8 の完全性は観測可能な subset の呼称にしない。提供元が報告しない呼出しがある場合は、
その欠落を残し、「全呼出しを追跡済み」とは判定しない。

### 現時点の評価と証拠

以下は上記 baseline のコード上の評価であり、全構成の実運用受入れではない。
今後の進捗と完了証拠は関連 Issue / PR に記録し、この初期評価と区別する。

| 要素 | 初期評価 | 主な根拠と残る要求 |
| --- | --- | --- |
| H1 | 概ね充足、runtime に委譲 | `internal/runtime/runtime.go`、`controller/run.go`、`controller/reviewflow.go`。内側のツール反復と外側の役割遷移を接続した実動作・異常時の証拠が必要。 |
| H2 | 部分充足 | `copilot/copilot.go` の tool / file policy と `openacp/sandbox_linux.go` の隔離。全対応構成のタスク隔離と、ターミナル・ブラウザ・接続アプリの能力の差が残る。 |
| H3 | 部分充足 | `controller/reviewflow.go`、`controller/context.go`。役割 session と構造化引継ぎはあるが、独立サイドタスクの並列委譲ではない。固定 ToolPolicy の `copilot/tools.go` は子エージェント用ツールを拒否する。 |
| H4 | 概ね充足、runtime に委譲 | `controller/context.go` と `copilot/copilot.go` の role projection、skill 設定、Infinite Sessions。毎ターンの選択と圧縮前後の必須契約保持は runtime 別に受入れが必要。 |
| H5 | 概ね充足 | `internal/memory/`、`controller/restart_test.go`、`controller/review_progress.go`。新 session、成果保全、移送を含む継続の通し受入れが残る。 |
| H6 | 部分充足 | ApprovalBundle、公開ゲート、`copilot/credentials.go`、tool policy。承認と redaction は、全 runtime で認証情報が隔離される証拠にはならない。 |
| H7 | 実装 Flow では強く充足 | `controller/controller.go` の `Finish` と `controller/reviewflow.go` の同一対象の独立レビュー。検証項目の十分性、ブラウザ検証、model-free の申告との区別を確認する。 |
| H8 | 部分充足 | `controller/receipts.go`、`controller/evaluation.go`、`controller/progress_monitor.go`。完全な呼出し追跡と意味的な停滞検知・方針変更は未充足。Copilot の compaction event は生成されるが標準 `StreamEvents` の DB 保存対象には入っていない。 |

この表の `controller/`、`copilot/`、`openacp/` は `internal/runtime/` 配下を指す。
テストファイルの存在は受入れ実行の証拠とは扱わない。

### 分割作業と要求の維持

8要素を親 Issue で追跡し、H8 は呼出し追跡と停滞への対処に分ける。
各子 Issue は、対象 ID、現状の根拠、担当範囲、受入れ条件、既存 Issue との対応、
依存関係と単独で着手する方法を持つ。全要素の一括変更を前提にしない。
共有 interface が必要なら、その最小契約を先に記録し、別 Issue 全体の完成を前提にしない。

延期は着手時期の変更であり、要求の対象外化ではない。
担当範囲外の要求は所有する Issue へ明示して引き継ぎ、追跡先のない対象外を作らない。
既存 Issue に統合する場合も、個別の判定項目と未達の受入れ条件を移して相互参照する。
実装済みの部分を再実装せず、残る差分と実受入れだけを作業対象にできる。

完了時は runtime / OS / tool 構成、対象成果物、検証結果、残る欠落を明示する。
未対応・未観測・失敗・利用者申告を成功に読み替えない。
要求の削除・縮小には理由を伴う明示的な再判断と ADR の改訂を必要とし、
「主要な役割ではない」「今回は実装しない」という説明だけでは削除しない。
親 Issue は未達条件が残る間は完了にしない。

この判断は即時の実装順、リリース期限、追加予算を定めない。
各作業は承認済みの目的・権限・残予算・期限に従い、製品開発を止めない単位で進める。

## Alternatives considered

8要素を Taxion 内へ直ちに再実装する案は採用しない。
既存 SDK / OS の責任を重複実装し、製品開発よりハーネス開発を優先することになるためである。

Taxion を承認管理だけに限定して不足項目を対象外にする案も採用しない。
採択した利用者要求の隔離・委譲・継続・適応が、後続の判断から失われるためである。

## Consequences

設計・runtime 選定・更新時に同じ8要素で比較できる。
未充足の要求は独立した作業として残り、一部の実装完了や委譲を全体の完成と混同しない。
進捗記録は Issue / PR、利用可能な機能は現在の仕様文書に置き、この ADR を機能一覧にしない。

## Security and operational impact

worktree 分離、permission callback、credential redaction、OS 隔離を別の対策として評価する。
認証情報をモデルに渡さない設計と、必要な外部操作を仲介する仕組みを検討対象に含める。
観測用の記録にも秘密を残さず、完全性の確認のために秘密の保存や追加権限を要求しない。
停滞の検知は新しい実行権限、修正枠、課金上限の解除を意味しない。

## Compatibility

今回は判断基準と後続作業の記録だけを追加し、CLI、DB schema、保存済み承認、
runtime 設定、実行経路を変更しない。
ADR-0003 の責任分離、ADR-0020 の Memory と役割分離、
ADR-0038 の runtime 固有の隔離、ADR-0055 の承認済み範囲内の適応、
ADR-0061 の model-free 申告の限界を維持する。
