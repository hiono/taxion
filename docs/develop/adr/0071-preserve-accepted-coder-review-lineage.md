# ADR-0071: 受理済み Coder 出力の差分基点と未開始 Reviewer を保持して継続する

## Context

通常 Flow の `git-diff-v1` は、元 baseline A から完全 tree T までの変更を受理する。
Coder の実行 commit B が A と異なる場合、Reviewer の実行場所は B を HEAD とするが、
照合する全変更パスの差分基点は A のままである。
この区別が持込み成果物にしかなく、通常 Coder 出力では B から T までの差分を
全変更パスと比較して準備を拒否していた。

準備失敗後の未開始 Reviewer は、既存の持込み成果物専用復旧には該当せず、
通常後続の承認も未取消の指示を理由に拒否する。
受理済み結果を再生成することや、DB を直接編集することは解決にしない。

## Decision

新しく発行する Reviewer 指示へ、既存の hash 付き target schema を用いた
`coder-review-target:` decision を保存する。A、B、T、全変更パス、repository、
成功 Coder の出典を結び付け、元結果と照合する。
Reviewer の HEAD と実 index は B、完全 tree は T、差分照合の基点は A を維持する。

既存の `reconcile-stopped` を、通常 Flow の受理済み Coder に続く未開始 Reviewer に限定して広げる。
静止証拠と配信・利用量の不確実性への承認、preview hash、受理 receipt と Git 証拠を確認して
Reviewer だけを取り消す。旧 Flow/HOLD、親の `WAITING_FOR_REVIEW`、成功結果、検証と履歴を保持する。
後続は既存の intake/confirm と `continueFromDispatchId` を用い、受理 receipt を後続承認と開始時にも再照合する。
Coder と受理済み検証は再実行せず、通常の Reviewer 結果受理ゲートは維持する。

レビューのみ、repair0 の後続の Coder 枠は0とする。
承認 JSON の任意 `deadline` は工程 hash に含めた固定上限であり、
`timeoutSeconds` はそれを短縮できるだけである。旧期限が切れた場合は、将来期限を別途明示承認する。

### 差分・対象パスの条件表

A は Coder の元 baseline、B は受理済み出力 commit、T は受理済み完全 tree、
P は Controller が A→T から導出した全変更パス、R は Coder が今回申告したパスとする。
以下は個々のパスの種類による許可表ではなく、対象全体の照合条件を組み合わせた決定表である。
「○」はこの照合条件を満たすことを表し、identity・承認・予算などの別ゲートの省略を意味しない。
「×」の条件が一つでもあれば拒否する。例の4パス・28パスは固定上限ではない。

| ID | 条件 | 作業場所の準備 | 全変更パスの照合 | 判断 |
| --- | --- | --- | --- | --- |
| P1 | A＝B、T・P・出典が一致 | HEAD と index は B、B→T を適用 | A→T＝P | ○ |
| P2 | A≠B、dirty snapshot の T・P・出典が一致 | HEAD と index は B、B→T を適用 | A→T＝P | ○。A≠B 自体は拒否理由にならない |
| P3 | commit 済み target の T・P・出典が一致 | 出力 commit B の tree が T と一致することを確認 | A→T＝P | ○ |
| P4 | R は今回の4パス、P は持越しを含む28パスで、受理済み manifest と一致 | 完全 T を再現 | P を維持し、R は申告情報として別に保持 | ○。R と P の差だけを不整合としない |
| P5 | A→T＝P だが、A≠B のため B→T≠P | B→T の適用は正しい | B→T を P と比較する判定は採用しない | ○。A→T と照合する |
| P6 | P を R に縮小、または申告だけで全変更を確定 | 縮小した対象は使用しない | 完全な A→T を満たさない | × |
| P7 | T・P・manifest・出典・hash が不一致、または必要な証拠が未確定 | 準備・開始を進めない | 保存結果と Git 証拠の両方を必要とする | × |

B→T は snapshot を作業場所へ再現する差分であり、それ自体が誤りなのではない。
レビュー対象の全変更パス P を照合する基点 A と、実行場所の基点 B を混同したことが今回の原因である。

### 未開始取消・レビュー後続の条件表

この表は通常 Coder Flow の `reconcile-stopped` と、その成功 Coder を継承する後続に限定する。
○の行でも、受理 receipt と同じ A/B/T/P、静止証拠、不確実性への承認、正確な preview hash、
取消 audit、所有権・設定・費用の承認をすべて必要とする。表は状態の全直積を列挙したものではない。

| ID | 旧 Reviewer／Flow | 管理 worktree | 期限・後続 | 未開始取消 | レビューのみの後続 |
| --- | --- | --- | --- | --- | --- |
| R1 | ISSUED、ACK・開始・session・runtime receipt・結果・利用量記録なし、STOPPED/HOLD、runner なし | 未準備で実パスも存在しない | 承認された将来の固定期限 | ○ | ○。取消後に別途承認 |
| R2 | 同上 | 準備記録あり、登録・repository・detached HEAD・index・完全 T・余分／ignored ファイルの照合を満たす | 承認された将来の固定期限 | ○。既存 worktree を保持 | ○。新しい独立レビュー場所で開始 |
| R3 | 同上 | 上記のどちらかの整合した状態 | 旧期限切れ、新期限を明示承認 | ○。旧 Flow は復活させない | ○。新期限と工程 hash を承認 |
| R4 | 同上 | 整合した状態 | 新期限切れ、または承認後に期限・工程 hash が変化 | ○。取消に必要な承認は別途必要 | ×。新しい実効計画の承認が必要 |
| R5 | ACK・開始・session・runtime receipt・結果・利用量記録のいずれかあり | 任意 | 任意 | ×。未開始契約の対象外 | この取消経路では不可。別の正式な実行整合が必要 |
| R6 | runner・active 実行・所有権が未解決 | 任意 | 任意 | × | × |
| R7 | 未開始・停止条件は満たす | 実パスはあるが準備記録なし、準備状態不明、または Git／ファイルが drift | 任意 | ×。削除せず保持 | × |
| R8 | source receipt・manifest・契約・A/B/T/P が欠落または不一致 | 任意 | 任意 | × | ×。取消後の receipt 欠落も拒否 |
| R9 | 静止証拠・不確実性への承認・preview hash が不足または古い | 任意 | 任意 | × | × |
| R10 | 取消 audit・完全な CANCELLED target・後続の設定／費用／期限承認が不足 | 任意 | 任意 | 既に取消済みなら再取消しない | × |

記録なしは「未送信」「利用量ゼロ」の証明ではない。後続は Coder0・Reviewer1・repair0とし、
元の成功検証は再実行せず、通常の Reviewer 結果受理ゲートを維持する。
持込み成果物専用の `recover-review` の適用可否は、この表から推定しない。

### 関連する復旧判断と遷移境界

[ADR-0054](0054-reconcile-stopped-dispatch-input.md) は初回 Coder の承認済み入力、
[ADR-0058](0058-recover-unstarted-artifact-review.md) は持込み成果物と停止レビュー、
[ADR-0052](0052-accept-saved-review-without-restarting-execution.md) は限定された保存済み成功レビューの受理を扱う。
Issue #194、#213、#238、#240、#242、#185 の判断と、本修正の PR #263 を比較すると、
「保存成果から続ける」という共通目的でも、成果の出典と実行段階によって許可する遷移が異なる。
本 ADR はこれらの適用範囲を一律に広げず、通常 Coder の受理済み出力が未開始 Reviewer で停止した境界を補う。

| 境界 | 保存証拠・状態 | 許可する判断 | 流用しない判断 |
| --- | --- | --- | --- |
| G1: 承認済み入力から未開始 Coder が停止 | 入力の承認・snapshot、初回 ISSUED、静止と不確実性 | ADR-0054 の取消と入力継承 | 入力を成功 Coder の成果とみなす |
| G2: 受理済み Coder から未開始 Reviewer が停止 | 成功 result と受理 receipt、A/B/T/P、未開始・停止条件 | 本 ADR の取消と成功 Coder 継承 | 持込み成果物専用復旧、旧指示の書換え |
| G3: 持込み成果物 Reviewer が停止 | 承認した入力・検証状態、未開始または正式な実行停止 receipt | ADR-0058 の適用条件を満たす `recover-review` | 通常 Coder Flow への無条件適用 |
| G4: 稼働中の同じ実行の期限・予算不足 | 同一 runner・session・指示、現在の工程期限内の承認 | ADR-0058 の `extend` | 終端実行の復活、別実行への承認流用 |
| G5: 保存済み成功レビューの正式受理が停止 | ADR-0052 の限定された停止原因、期限内の成功 receipt と同一対象 | 適用条件を満たす `accept-saved-review` | 任意の停止を成功受理、再レビューで証拠を再取得 |

今回の差分基点の混同と、独立レビューで見つかった取消後の source receipt 再照合漏れは、
異なる不具合である。前者は証拠の意味を次工程で変えた問題、後者は前工程の確認を後工程でも
成立していると扱った問題であり、一つの根本原因と断定しない。

### 証拠の保持と再照合の条件表

[RC 全16版の履歴監査](../rc-decision-boundary-audit.md)では、対象照合、復旧対象の限定、
期限、非同期処理、認可、品質完了を別の問題として比較した。
既存 ADR に全工程の照合方針があったことも確認したため、方針文の追加だけを対策とはしない。
次の表は本 ADR の通常レビュー経路に対する確認責務であり、新しい保存形式や操作ではない。

| ID | 照合点 | 正本として使う証拠 | 許可の境界と拒否後の保持 |
| --- | --- | --- | --- |
| E1 | Coder の正式受理 | 元 instruction、Controller manifest、実 Git、検証 receipt | 申告 R と確定 P を分離。未受理提出・失敗を成功にしない |
| E2 | Reviewer 指示の生成・準備 | 成功 Coder の A/B/T/P と受理 receipt | 再現 B→T と全変更 A→T を分離。旧指示・結果を変更しない |
| E3 | 未開始取消の preview と適用 | 現在の停止・所有権・準備状態、同じ source receipt、承認 hash | 両時点で確認。drift・開始済みなら停止状態と worktree を保持 |
| E4 | 後続の intake と confirm | 取消 audit、完全 target、同じ受理済み Coder、後続の設定と承認 | preview の成功を確定許可にしない。receipt 欠落は拒否 |
| E5 | 工程計画と start | 同じ A/B/T/P、現在の receipt、実効計画 hash、固定期限・累計枠 | 旧 Flow は停止のまま。旧期限切れは明示承認した将来期限で後続 |
| E6 | 新 Reviewer の結果受理 | 独立した指示・結果、同一対象の受入れ証拠、通常の受理検証 | 元 Coder 検証の保持は、新 Reviewer の受理検証を省く理由にならない |
| E7 | 品質・公開判定 | 対象に結び付いた必須条件・検証・独立レビュー・別の公開承認 | レビュー成功や診断完了だけで品質・公開を合格にしない |

今後これらの境界を変更する際は、入力の出典、対象の基点、検証状態、停止地点、
所有権と不確実性、旧・新期限、承認差分、再照合点、拒否後の保存状態を決定表へ対応付ける。
既存の許可例に一条件だけを変えた拒否例、別の出典の隣接経路、
前段の合格後に証拠を変更・欠落させた例を、影響する正式操作まで追う。
各行を実装済み・未対応・未確認に分け、試験名と到達した終点を記録する。
全直積の試験や、未実施の実サービス受入れを主張しない。

独立レビューは完成した表、対応するコード・試験、履歴上の反例を対象にする。
許可と拒否だけでなく、実行なしの観測、診断完了、品質合格、公開許可を混同していないか確認する。
表や試験の追加自体を、未達の機能・運用・品質ゲートの完了とはしない。

### 後続 ADR での条件漏れを確認する

上記の確認責務は、後続 ADR が新しい復旧経路を追加する際にも適用する。
ADR-0072 の初版では、状態別の操作を列挙した一方、回答完了・失敗確定・接続終了を
一つの「完了」条件にまとめた。既存の表との整合だけでは、正当な非実行経路を拒否する
条件の過剰さを検出できなかった。この反例を既存の時間・非同期処理の確認責務へ追加する。

| 確認軸 | 表に必要な判断と反例 |
| --- | --- |
| 状態と証拠 | 保存回答、正式結果、停止証拠、所有権を別にする。同じ回答でも `RUNNING`・`CANCELLED`・`FAILED` の権限を流用しない |
| 時系列と出所 | 回答、turn 終了、失敗 event、正式 receipt、shutdown、観測を分け、順序・同時刻・欠落を比較する。時刻の正本を明記する |
| 期限と予約 | 元期限、保存済み延長、工程の提出期限、観測時刻を分ける。期限後の観測と期限後の実行を同じ理由で拒否しない |
| 実行との分離 | 回答完成後の接続終了と、新しい回答・tool 実行を比較する。main agent と子 agent の観測範囲も分け、観測・指摘保存が新実行や品質合格を許可しないことを確認する |
| 条件の独立性 | 許可例の一条件反転だけでなく、複数不成立、前後工程の相互作用、拒否条件を満たさなくても目的を安全に達成できる反例を検討する |
| 到達点と互換性 | preview・適用・再読取り・旧版読取りを分け、変更しない履歴と保存形式の拒否を確認する |

独立レビューでは、完成表を先に正解とせず、利用目的と保存証拠から検討軸・期待判断を
独立に導いてから表と照合する。意図した対象外と、未検討・未実装・未確認を区別し、
各拒否条件が保護する不変条件と、過剰拒否になる隣接例も確認する。
「全経路を列挙した」とだけ記載せず、列挙した軸、組合せの省略理由、反例、試験の到達点を残す。
この手順は未知の全経路を実証したという保証ではない。

## Alternatives considered

全変更パスを Coder の今回申告へ縮める、Git 照合を省略する、旧指示を書き換える、
Coder を再実行する、通常 Flow を持込み成果物専用復旧へ混在させる案は採用しない。
既存の取消と成功 Coder 継承が使えるため、新しい復旧サブシステムは追加しない。

## Consequences

旧版の不変な Reviewer 指示は再生成しない。安全に取消後、新しい後続指示に正しい出典を発行する。
完全 target が維持できない場合、ACK・実行・session・receipt がある場合、
未記録の管理 worktree が残る場合は拒否する。人の静止申告は未送信・無課金の証明ではない。

## Security and operational impact

identity、ownership、設定承認、利用量、期限、品質ゲートは維持する。
秘密、session 識別子、製品コード、運用機の原本は公開しない。
取消後にも source receipt が失われた場合は後続を拒否する。

## Compatibility

DB schema の変更はない。既存の持込み成果物と実行済み Reviewer の復旧契約は維持する。
新しい取消・指示・期限を扱う store は旧バイナリで操作しない。戻す場合は、適用前の整合バックアップを別配置で使う。
操作例は [CLI reference](../../userguide/cli-reference.md#受理済み-coder-出力からのレビュー継続)に一本化する。
