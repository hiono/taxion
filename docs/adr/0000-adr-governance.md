# ADR-0000: Architecture Decision Records の管理規約

Date: 2026-11-20

## Status

Accepted

## Context

Taxionは、人間の曖昧な意図を対話で整理し、複数のAgent / Roleの協調と安全境界によってJobの完遂を支援する製品です。設計判断、現行仕様、変更履歴、検証証拠を混在させると、過去の判断や検証結果を現行の正本と誤認します。また、利用者がアクセスできない非公開の外部資料を設計判断の根拠として参照すると、判断の意味や適用範囲を第三者が検証できません。

新Taxionの設計文書は、特定の非公開リポジトリ、外部ファイル、アカウント、個人の会話履歴へアクセスできることを前提にしてはなりません。必要な判断、理由、制約、代替案、受入条件は、新リポジトリ内で理解できるように記述します。

## Decision

### 1. ADRの役割

ADRは、現在採用しているアーキテクチャ上の判断、その理由、適用範囲、トレードオフおよび他の判断との関係を記録する正本とします。

ADRに記録しないもの:
- 作業進捗、TODO、ロードマップ、実験計画、時点依存のCI結果
- 現行仕様ではない過去の実装説明
- 未検証の仮説を実証済みとする記述
- コード・Issue・PR・検証証拠の代替となる詳細な作業ログ

### 2. ADRの必須構成

各ADRは次の規則に従います。

必須項目:
1. Title and number
2. Date
3. Status: Proposed / Accepted / Rejected / Superseded / Deprecated
4. Context
5. Decision
6. Consequences
7. Alternatives considered
8. Relationship to other ADRs

条件付き項目:
- Decision basis: 外部の公開資料や標準仕様に依存する場合、その識別情報と判断に用いた要点を記載します。非公開で読者が取得できない資料を根拠として要求しません。
- Security and operational impact: セキュリティまたは運用への影響がある場合は必須とします。
- Acceptance criteria: 実装・受入条件を規定する場合は必須とします。製品受入れシナリオの詳細はテスト仕様へ委ねます。

Decisionは採用する規則を肯定形で明示します。Contextは問題と制約を説明し、Consequencesは採用による影響を記述します。Alternatives consideredには、判断に影響した実質的な代替案と不採用理由を記録します。比較対象がない場合も、その旨と理由を明記し、見出しを省略しません。Relationship to other ADRsには、依存・具体化・置換・非変更の関係を記録します。実装の時点依存状態は含めません。

ADR本文だけで判断を理解できるようにし、参照先が取得不能になった場合でも判断の意味が失われない記述にします。公開仕様への参照を記載する場合も、判断に必要な要件・制約を本文に要約します。

### 3. 番号とファイル

- ADRは `docs/adr/NNNN-kebab-case-title.md` に保存します。
- 連番は本リポジトリ内で一意とします。
- 番号は識別子であり、優先順位や規範性を意味しません。
- ADRの一覧と関係は `docs/adr/README.md` に集約します。
- 採番済みADRの番号を再利用しません。内容の変更は既存ADRの改訂、または明示的な置換ADRで記録します。

### 4. 適用階層と衝突解決

- 製品目的を定めるADRが、個別の実装方式を暗黙に決めることはありません。
- 横断的な安全・整合性不変条件は、個別機能の利便性より優先します。
- より具体的なADRは、上位の目的を実現するための詳細を定めます。上位の安全境界を弱めてはなりません。
- 後続ADRが既存ADRを置換する場合、置換対象・範囲・維持する決定を明示します。番号の大小や作成日の新しさだけで全体を上書きしません。
- 衝突が解決するまで、実装は安全側の既存Accepted decisionに従い、矛盾する新規実装を追加しません。

### 5. 情報源と再現可能性

- 製品判断の規範的な根拠は本リポジトリ内のAccepted ADRと現行仕様に置きます。
- 非公開の外部リポジトリ、アクセス権が限定された文書、個人の会話履歴を、読者が参照しなければ判断を理解できない根拠として記載しません。
- 外部資料に由来する要件を採用する場合は、必要な要件・判断理由・適用範囲をADR本文に記述します。公開仕様や標準への参照は補助情報として扱います。
- 出所・利用条件・適用範囲を確認できない情報は、確定した設計判断として採用しません。
- 既存実装や候補実装を再利用する場合は、対象コード、provenance、利用条件、設計適合性、安全性、保守性および受入証拠を個別に確認します。存在や過去の成功報告だけで採用を決定しません。

### 6. 文書体系と規範性

| 文書 | 役割・規範性 |
|---|---|
| ADR | 採用したアーキテクチャ判断、その理由、適用範囲、トレードオフ、置換関係を記録します。 |
| 製品仕様 | 現在の製品動作、利用者との契約、ドメイン/APIの規範を定義します。 |
| テスト仕様 | 製品仕様とAccepted ADRへの適合を再現可能なシナリオで検証します。 |
| 開発・運用文書 | 開発手順、品質ゲート、API操作、調査・復旧手順など、変更可能な作業方法を定義します。 |
| 計画情報 | TODO、ロードマップ、開発計画、実験計画など、更新頻度の高い作業情報を保持します。 |
| GitHub Issue / PR / Actions | 作業経過、差分・レビュー、対象SHAに結び付いた実行証拠を保持します。 |

ADRはすべての情報の保管庫ではありません。ソース文書全体や運用手順をそのままADRへ複製せず、将来も有効な製品・アーキテクチャ判断だけを抽出します。現行動作の規範は製品仕様へ、再現可能な検証条件はテスト仕様へ、手順は開発・運用文書へ配置します。

### 7. 可変情報源と外部参照の有効性

TODO、ロードマップ、開発計画、実験計画などの可変情報について、特定の外部サービス、アカウント、フォルダー、文書名、URL、ローカルファイルを恒久的な正本として固定しません。

作業開始時には、計画情報の現在の所在、アクセス可能性、更新時点、対象プロジェクトとの対応を確認します。過去のURL、ファイル名、会話履歴、キャッシュ、以前の取得結果だけで、現在の存在・内容・アクセス権を推測しません。取得できない情報は未取得・未確認とし、それに依存する判断を保留します。独立して確定できるAccepted ADRと現行コードに基づく作業は継続できます。

外部参照先の変更や既存ファイルの移動・改名は、利用者の明示的な指示なしに実施しません。可変情報の保存方法は運用上の選択であり、製品設計判断として固定しません。

### 8. 情報記録の責務

各情報の具体的な保存・更新・証拠対応規則はADR-0009で定義します。本ADRは文書体系と統治原則を定め、ADR-0009は現行仕様、計画、変更履歴、Issue / PR、CI証拠の責務分離を具体化します。

## Consequences

- 本リポジトリ内のADRと仕様だけで、現行の製品設計判断を理解・検証できます。
- 判断に必要な情報を非公開の外部資料へ依存させません。
- ADRの正しさは文書の存在や相互リンクではなく、根拠・適用範囲・他ADRとの整合性で評価します。
- 実装開始前に、製品目的、ドメインモデル、協調、認可、安全、Provider、永続化、A2A、証拠・受入れのガードレールを確定します。

## Security and operational impact

秘密情報、認証・認可、Job境界、データ整合性、provenance、Providerの不確実な実行状態を妥協しません。自然言語の内容、Agentの自己申告、過去の履歴だけで権限を付与しません。未確認の事実・実行結果を確定事項として扱いません。

## Alternatives considered

- **非公開の外部資料をADRの必須根拠にする:** 読者が参照できず判断を検証できないため採用しません。
- **過去の会話や作業履歴を設計判断の正本にする:** 継続的な参照可能性・完全性・規範性を保証できないため採用しません。
- **すべての情報をADRへ複製する:** 可変情報や作業手順と恒久的な設計判断が混在するため採用しません。
- **外部参照を一切許可しない:** 公開標準や公開仕様の補助参照まで排除する必要はないため採用しません。ただし判断の意味はADR本文で完結させます。

## Relationship to other ADRs

本ADRはADR体系、文書の規範性、情報源の扱いを定めます。製品目的、Jobドメイン、認可、通信、Provider、永続化等の具体的な製品判断は各領域のADRで定義します。本ADRだけで製品機能や実装の完了を意味しません。
