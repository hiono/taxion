# ADR-0079: ドメイン不変条件を全状態変更経路で強制する

Date: 2026-11-13

## Status

Accepted

## Context

Taxion のドメインモデルでは、状態・権限・成果・証拠に関する規則を数式または論理条件として定義できる。Go はこれらの条件を表現できるため、定義した不変条件はコード上で評価・強制できる。

しかし、判定関数が存在することと、その条件がシステム全体で守られることは同じではない。Job completion readiness を評価する関数が存在していた一方、Job を `COMPLETED` に遷移させる経路および保存済み Graph を検証する経路の双方で条件が必須ゲートになっていなかった。このため、判定関数を経由しない状態変更によって、完了条件を満たさない Job が成立する余地があった。

これは数式化や表現能力の不足ではない。不変条件の定義、コード表現、すべての状態変更経路への適用を一貫して結び付ける設計規則が不足していた。

## Decision

Taxion のドメイン不変条件は、ドメインモデルの規範として扱い、状態を生成・変更・受入れ・復元するすべての経路で成立することを必須とする。

### 1. 規範と実装の対応

1. 不変条件は、対象状態、前提条件、成立条件、例外条件を明示した論理式または同等の形式で定義する。
2. コードはその定義を実行可能な形で表現する。判定関数の存在だけでは実装完了とみなさない。
3. 状態を変更する操作は、変更後の状態が不変条件を満たす場合に限り成立させる。
4. 保存データの読込み、移行、復元、外部入力も信頼境界として検証する。
5. 不変条件を満たさない場合は fail-closed とし、部分的な状態変更を残さない。

### 2. 強制箇所

不変条件の性質に応じて、少なくとも次の経路を評価する。

- 新規生成・初期化
- 状態遷移および関連データの更新
- Graph / aggregate の検証
- 永続化直前と永続化後の再読込み
- JSON 等の外部表現からの復元
- 旧形式からの移行、backup / recovery
- Controller / Runtime による実行直前の権限・予算・期限・scope の再検証
- 競合、再送、重複実行、実行状態不明からの復旧

すべての不変条件に同じ検証箇所を機械的に追加することは要求しない。各条件について、どの経路が状態を変更し、どの境界で強制するかを設計上明示する。

### 3. 判定・強制・検証の区別

次の三つを別々の完了条件として扱う。

- **判定:** 不変条件を評価する規範的な判定ロジックがある。
- **強制:** 不変条件に違反する状態変更・保存・実行を成立させない。
- **検証:** 正常系と違反系を含め、対象となる全経路で強制されることをテストおよびコードレビューで確認できる。

違反を検出するだけの validator と、違反状態の生成を防ぐ mutation gate は役割が異なる。必要に応じて両方を設ける。復元時の検証は、過去に保存された不正状態を現在のモデルへ持ち込ませないために必要である。

### 4. テストと証拠

- 正常条件を満たす状態変更が成功することを確認する。
- 不変条件に違反する状態変更が拒否されることを確認する。
- 拒否後に元の状態・履歴・永続データが変更されていないことを確認する。
- 不正な保存データ・外部入力・移行データの復元が拒否されることを確認する。
- 同じ不変条件を複数の経路から検証し、経路ごとのテスト対象を追跡可能にする。
- テストが通った事実だけで全経路の網羅を主張しない。実装上の入口と呼出し関係を調査し、未確認経路を明示する。

### 5. 適用範囲

本決定は Job、Task、RoleExecution、JobApproval、JobOutput、JobEvidence および今後追加するドメインモデルに適用する。認証・認可、承認、秘密情報、データ整合性、二重実行防止、不可逆操作、予算、期限、成果物 provenance などの安全・運用条件は必須不変条件として扱う。

## Alternatives considered

- **判定関数の存在を実装完了とみなす:** 呼び出されない経路が残り得るため採用しない。
- **保存時 validator のみで担保する:** 不正状態を一度生成してから拒否する構造となり、外部副作用との不整合を招くため、状態変更時の gate と併用する。
- **各 Controller が個別に同じ条件を再実装する:** 判定の分岐・意味の不一致を招くため、ドメインの規範的な判定ロジックを共有する。
- **すべての性質を一つの巨大な validator に集約する:** 責務境界と実行時に必要な再検証点を曖昧にするため採用しない。

## Consequences

- ADR の論理条件、ドメイン判定、状態変更 gate、Graph validation、テストを追跡可能にする。
- 判定関数があっても未適用経路があれば未完了として扱う。
- 状態変更の入口と復元境界の棚卸しが必要となる。
- 不変条件の変更時には、影響する全経路と既存データへの影響を再評価する。
- テスト成功は重要な証拠だが、未調査の経路を含む全体保証とは区別する。

## Security and operational impact

安全に関する不変条件を利便性・性能・変更量で相殺しない。権限、承認、秘密情報、scope、予算、期限、二重実行、不可逆操作、実行状態不明は、対象操作の直前にも現在の状態に基づいて検証する。検証不能な場合は実行を許可しない。

## Compatibility

既存データの読み込み・移行はデータ保全のために扱うが、旧形式に不正な状態が含まれる場合に新しい不変条件を無効化して受け入れてはならない。必要な場合は明示的な移行・修復を行い、暗黙に正当化しない。

## Status

Accepted. Job completion is the first explicit application: the transition gate and persisted Graph validation both enforce the completion-readiness predicate. The invariant map records the current implementation and verification evidence; other domain invariants must be audited against this decision as their implementation proceeds.
